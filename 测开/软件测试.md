# 接口测试

## 什么是接口？

接口可以理解为“两个系统、两个模块之间沟通的通道”。

在软件里，一个功能通常不是单独完成的，而是由前端页面、后端服务、数据库、第三方系统等一起配合完成。它们之间传递数据、请求服务的入口，就叫接口。

举个例子：

我们在登录页面输入账号和密码，点击“登录”按钮。页面本身不会判断账号密码是否正确，它会把账号和密码发送给后端的登录接口。后端接口收到数据后，会去判断账号密码是否正确，然后返回结果。

比如登录接口可以简单理解为：

- 请求地址：`/api/login`
- 请求数据：账号、密码
- 返回结果：登录成功、登录失败、用户信息、登录凭证等

所以，接口的本质就是：一方按照约定发送数据，另一方按照约定处理并返回结果。





## 什么是接口测试，为什么要进行接口测试？

接口测试就是测试接口是否能按照约定正常工作。

测试时，我们不一定通过页面操作，而是直接向接口发送请求，然后检查接口返回的数据是否正确、状态是否正确、业务逻辑是否正确。

还是以登录接口为例，我们可以测试：

- 输入正确账号和密码，是否返回登录成功
- 输入错误密码，是否返回登录失败
- 不输入账号，是否提示账号不能为空
- 密码为空，是否提示密码不能为空
- 已冻结的账号，是否不能登录
- 返回结果中是否包含正确的用户信息

为什么要进行接口测试？

1. 接口是前后端交互的核心

   页面上的很多功能，背后都是接口在处理。比如登录、注册、下单、支付、查询订单等。如果接口出问题，页面功能也很可能出问题。

2. 可以更早发现问题

   有时候前端页面还没开发完，后端接口已经完成了。这时测试人员可以先测接口，不用等页面全部做好。

3. 测试更直接

   功能测试通常要点页面、填表单、点按钮。接口测试可以直接给接口传数据，检查返回结果，更容易定位问题是前端问题还是后端问题。

4. 可以覆盖一些页面不好操作的场景

   比如金额传负数、手机号格式错误、订单状态异常、用户权限不正确等。这些数据通过页面不一定容易构造，但接口测试可以直接发送这些特殊数据。

简单来说，接口测试就是绕过页面，直接检查系统内部的数据处理是否正确。





## 接口测试与功能测试的区别

功能测试主要站在用户角度，验证页面功能是否能正常使用；接口测试主要站在数据交互角度，验证接口的请求和响应是否正确。

举个例子：测试登录功能。

功能测试会这样测：

- 打开登录页面
- 输入账号和密码
- 点击登录按钮
- 观察是否跳转到首页
- 检查页面是否显示用户名

接口测试会这样测：

- 直接请求登录接口 `/api/login`
- 传入账号和密码
- 查看接口返回的状态码、返回数据、错误提示
- 检查登录成功时是否返回 token 或用户信息
- 检查登录失败时是否返回正确的错误信息

两者的区别可以这样理解：

| 对比点 | 功能测试 | 接口测试 |
| --- | --- | --- |
| 测试角度 | 从用户使用角度出发 | 从数据交互和业务逻辑角度出发 |
| 是否依赖页面 | 通常依赖页面 | 不一定依赖页面 |
| 测试方式 | 点页面、填数据、看结果 | 发请求、传参数、看响应 |
| 发现问题位置 | 发现页面或整体功能问题 | 更容易发现后端接口、数据处理问题 |
| 测试效率 | 手工操作较多，速度相对慢 | 可以直接构造数据，效率较高 |
| 适合阶段 | 页面完成后测试 | 接口完成后就可以测试 |

可以用一句话记住：

功能测试看“用户能不能正常用”，接口测试看“系统之间传数据和处理数据对不对”。









## ⭐HTTP

HTTP 全称是 HyperText Transfer Protocol，中文叫“超文本传输协议”。简单理解：HTTP 是客户端和服务器之间传递数据时遵守的一套规则。

在接口测试里，我们经常用 Postman、Apifox、JMeter、curl 等工具发送 HTTP 请求，然后查看服务器返回的 HTTP 响应。

比如：

用户在 App 或网页上点击“登录”按钮，本质上可能就是客户端向服务器发送了一个 HTTP 请求；服务器处理完之后，再返回一个 HTTP 响应，告诉客户端登录成功还是失败。

HTTP 消息主要分为两类：

- HTTP 请求：客户端发给服务器，请服务器执行某个操作
- HTTP 响应：服务器返回给客户端，告诉客户端处理结果

HTTP 请求和响应的结构很相似，通常都包含：

- 起始行：说明请求动作，或者说明响应状态
- 头部 Header：描述请求或响应的附加信息
- 空行：表示头部结束
- 主体 Body：真正传输的数据，不是每个请求或响应都有

### HTTP 请求

HTTP 请求就是客户端向服务器发送的一段消息，用来告诉服务器“我要做什么”。

接口测试时，在 Postman 里创建一个请求，一般要重点关注：

- 请求方法 Method
- 请求地址 URL
- 请求头 Headers
- 请求参数 Params
- 请求体 Body
- 鉴权信息 Authorization

#### 1. 请求方法 Method

请求方法表示这次请求想让服务器做什么操作。

常见请求方法：

| 方法 | 含义 | 常见场景 |
| --- | --- | --- |
| GET | 获取资源 | 查询用户信息、查询商品列表 |
| POST | 提交数据 | 登录、注册、新增订单 |
| PUT | 整体更新资源 | 修改完整用户资料 |
| PATCH | 部分更新资源 | 只修改用户昵称、手机号 |
| DELETE | 删除资源 | 删除地址、删除订单 |
| HEAD | 只获取响应头，不获取响应体 | 检查资源是否存在 |
| OPTIONS | 查询服务器支持哪些方法 | 跨域预检、接口能力检查 |

测试人员重点要明白：

- 查询类接口通常用 GET
- 新增或提交类接口通常用 POST
- 修改类接口常见 PUT 或 PATCH
- 删除类接口通常用 DELETE
- 实际项目中以后端接口文档为准，不要只靠方法名猜

例如查询用户信息：

```http
GET /api/users/1001 HTTP/1.1
Host: example.com
Authorization: Bearer token123
```

表示：向 `example.com` 服务器请求 `/api/users/1001` 这个资源，也就是查询 ID 为 `1001` 的用户。

#### 2. 请求地址 URL

URL 就是接口地址。

一个完整 URL 例子：

```text
https://api.example.com/api/users?page=1&size=10
```

可以拆成：

- `https`：协议
- `api.example.com`：域名
- `/api/users`：接口路径
- `page=1&size=10`：查询参数

在 Postman 里，URL 通常写在请求方法右边的地址栏中。

测试人员需要重点检查：

- 域名是否正确，比如测试环境、预发环境、生产环境不要混用
- 接口路径是否正确
- 查询参数是否正确
- 参数是否需要 URL 编码，比如中文、空格、特殊符号

#### 3. 请求参数 Params

请求参数是发给服务器的数据之一。

GET 请求常把参数放在 URL 后面：

```text
/api/products?keyword=手机&page=1&size=20
```

含义：

- `keyword=手机`：搜索关键词是手机
- `page=1`：第 1 页
- `size=20`：每页 20 条

在 Postman 里，可以在 Params 页签里填写参数，工具会自动拼接到 URL 后面。

测试时可以关注：

- 必填参数不传会怎样
- 参数为空会怎样
- 参数类型错误会怎样，比如页码传成字符串
- 参数边界值会怎样，比如 `page=0`、`size=9999`
- 特殊字符会怎样，比如中文、空格、符号

#### 4. 请求头 Headers

请求头用于补充说明这次请求的信息。它不是主要业务数据，但会影响服务器如何处理请求。

常见请求头：

| 请求头 | 作用 |
| --- | --- |
| `Content-Type` | 告诉服务器请求体是什么格式 |
| `Accept` | 告诉服务器客户端希望接收什么格式的数据 |
| `Authorization` | 传递登录凭证或 token |
| `Cookie` | 传递浏览器保存的会话信息 |
| `User-Agent` | 说明客户端类型，比如浏览器、App、工具 |
| `Host` | 说明访问的服务器域名 |

测试人员最常接触的是：

```http
Content-Type: application/json
Authorization: Bearer token123
```

含义：

- `Content-Type: application/json`：请求体是 JSON 格式
- `Authorization: Bearer token123`：带上登录凭证，证明当前用户身份

如果接口需要登录，但请求头里没有 token，服务器通常会返回 `401 Unauthorized`。

#### 5. 请求体 Body

请求体是真正提交给服务器的数据。不是所有请求都有 Body。GET 请求通常没有 Body，POST、PUT、PATCH 请求通常会有 Body。

登录接口请求体例子：

```json
{
  "username": "test001",
  "password": "123456"
}
```

完整请求大概长这样：

```http
POST /api/login HTTP/1.1
Host: example.com
Content-Type: application/json

{
  "username": "test001",
  "password": "123456"
}
```

注意中间有一个空行。空行上面是请求头，空行下面是请求体。

Postman 里 Body 常见类型：

| Body 类型 | 说明 | 常见场景 |
| --- | --- | --- |
| none | 没有请求体 | GET 查询 |
| form-data | 表单数据，可以上传文件 | 文件上传、带文件的表单 |
| x-www-form-urlencoded | 普通表单键值对 | 传统表单提交 |
| raw JSON | 原始 JSON 数据 | 大多数前后端分离接口 |
| binary | 二进制文件 | 上传单个文件 |

接口测试时，Body 要重点检查：

- 字段名是否正确
- 字段类型是否正确，比如数字不要传成字符串
- 必填字段是否都传了
- 空值、null、超长字符串是否能正确处理
- JSON 格式是否正确，比如双引号、逗号、括号是否完整
- `Content-Type` 是否和 Body 类型一致

### HTTP 响应

HTTP 响应是服务器处理请求后返回给客户端的消息。

在 Postman 里发送请求后，下方看到的结果就是响应。测试人员要重点看：

- 状态码 Status Code
- 响应头 Headers
- 响应体 Body
- 响应时间 Time
- 响应大小 Size

#### 1. 状态行和状态码

响应的第一行叫状态行，表示服务器处理结果。

例子：

```http
HTTP/1.1 200 OK
```

含义：

- `HTTP/1.1`：HTTP 版本
- `200`：状态码
- `OK`：状态文本

常见状态码：

| 状态码 | 含义 | 测试时怎么理解 |
| --- | --- | --- |
| 200 | 请求成功 | 查询、登录等接口正常返回 |
| 201 | 创建成功 | 新增用户、新增订单成功 |
| 204 | 成功但没有响应体 | 删除成功但不返回内容 |
| 301/302 | 重定向 | 请求被跳转到其他地址 |
| 400 | 请求参数错误 | 参数格式错、缺少必填字段 |
| 401 | 未认证 | 没登录、token 缺失或无效 |
| 403 | 无权限 | 登录了，但没有访问权限 |
| 404 | 资源不存在 | URL 错误或数据不存在 |
| 405 | 方法不允许 | 该接口不支持当前请求方法 |
| 409 | 资源冲突 | 重复注册、重复提交 |
| 500 | 服务器内部错误 | 后端程序异常 |
| 502/503/504 | 网关或服务不可用 | 服务挂了、超时、网关异常 |

注意：状态码只能说明 HTTP 层面的处理结果，不一定完全等于业务结果。

例如有些项目登录失败也返回 `200`，但响应体里会写：

```json
{
  "code": 10001,
  "message": "密码错误",
  "success": false
}
```

所以测试接口时不能只看状态码，还要看响应体里的业务字段。

#### 2. 响应头 Headers

响应头是服务器返回的附加信息。

常见响应头：

| 响应头 | 作用 |
| --- | --- |
| `Content-Type` | 响应体的数据格式 |
| `Content-Length` | 响应体大小 |
| `Set-Cookie` | 服务器让客户端保存 Cookie |
| `Cache-Control` | 控制缓存策略 |
| `Location` | 重定向地址 |
| `Access-Control-Allow-Origin` | 跨域相关配置 |

例如：

```http
Content-Type: application/json
Set-Cookie: sessionId=abc123
```

表示服务器返回的是 JSON 数据，并且让客户端保存一个 Cookie。

测试人员需要关注：

- `Content-Type` 是否正确
- 登录后是否正确返回 token 或 Cookie
- 下载文件时文件类型是否正确
- 重定向时 `Location` 是否正确
- 跨域接口是否返回正确的跨域响应头

#### 3. 响应体 Body

响应体是服务器真正返回的数据。

登录成功响应例子：

```json
{
  "code": 0,
  "message": "登录成功",
  "data": {
    "userId": 1001,
    "username": "test001",
    "token": "token123"
  }
}
```

测试时要检查：

- `code` 是否符合接口文档
- `message` 提示是否正确
- `data` 数据是否完整
- 字段类型是否正确，比如 `userId` 应该是数字
- 不该返回的敏感信息是否没有返回，比如密码
- 错误场景是否返回清晰的错误信息

登录失败响应例子：

```json
{
  "code": 10001,
  "message": "用户名或密码错误",
  "data": null
}
```

测试时要确认：

- 错误码是否正确
- 错误提示是否正确
- 不应该返回 token
- 不应该登录成功

### 用 Postman 测一个登录接口的例子

假设接口文档如下：

- 请求方法：`POST`
- 请求地址：`https://api.example.com/api/login`
- 请求头：`Content-Type: application/json`
- 请求体：

```json
{
  "username": "test001",
  "password": "123456"
}
```

在 Postman 中可以这样操作：

1. Method 选择 `POST`
2. URL 输入 `https://api.example.com/api/login`
3. Headers 添加 `Content-Type: application/json`
4. Body 选择 `raw`
5. Body 格式选择 `JSON`
6. 输入 JSON 请求体
7. 点击 Send
8. 查看状态码、响应体、响应时间

期望结果：

```http
HTTP/1.1 200 OK
Content-Type: application/json
```

```json
{
  "code": 0,
  "message": "登录成功",
  "data": {
    "token": "token123"
  }
}
```

可以设计的测试用例：

| 用例 | 请求数据 | 预期结果 |
| --- | --- | --- |
| 正确账号密码 | 正确 username、正确 password | 登录成功，返回 token |
| 错误密码 | 正确 username、错误 password | 登录失败，不返回 token |
| 用户名为空 | username 为空 | 提示用户名不能为空 |
| 密码为空 | password 为空 | 提示密码不能为空 |
| 少传字段 | 不传 password | 提示必填参数缺失 |
| JSON 格式错误 | 少一个右括号 | 返回请求格式错误 |
| 未设置 Content-Type | 不传 `Content-Type` | 可能解析失败或返回参数错误 |

### 测试人员看 HTTP 请求和响应时的重点

接口测试不要只点 Send，要有检查点。

请求方面重点看：

- 方法是否正确：GET、POST、PUT、DELETE 是否和接口文档一致
- URL 是否正确：环境、域名、路径、参数是否正确
- Params 是否正确：必填、选填、边界值、特殊值
- Headers 是否正确：尤其是 `Content-Type`、`Authorization`、Cookie
- Body 是否正确：字段名、字段类型、字段值、JSON 格式
- 鉴权是否正确：是否需要 token，token 是否过期，权限是否足够

响应方面重点看：

- 状态码是否合理
- 业务 code 是否正确
- message 是否符合预期
- data 字段是否完整、准确
- 数据类型是否正确
- 是否泄露敏感信息
- 响应时间是否可接受
- 错误场景是否有明确提示

### 一个容易混淆的点：状态码和业务码

状态码是 HTTP 协议层面的结果，比如 `200`、`404`、`500`。

业务码是系统自己定义的结果，比如：

```json
{
  "code": 10001,
  "message": "密码错误"
}
```

有些公司会这样设计：

- HTTP 状态码 `200`：请求到达服务器，并且服务器正常返回
- 业务 code `0`：业务成功
- 业务 code 非 `0`：业务失败

所以接口测试时要同时看：

- HTTP 状态码
- 响应体中的业务 code
- 响应体中的 message
- 响应体中的 data

### 小结

HTTP 请求可以理解为：客户端告诉服务器“我要做什么，并把需要的数据给你”。

HTTP 响应可以理解为：服务器告诉客户端“我处理完了，结果是这样”。

对测试人员来说，学习 HTTP 的重点不是背概念，而是能看懂一次接口调用：

- 请求方法是什么
- 请求地址是什么
- 参数传在哪里
- 请求头有什么作用
- 请求体是什么格式
- 响应状态码是什么意思
- 响应体里的业务结果是否正确

#### API

**添加一个接口**

在编辑界面，添加一个接口地址（New），可以设置请求头，参数，点击 send 就发送了，请求。下半部分能看到响应体，响应头，状态码等信息。例如 GET https://www.ixuea.com

## 接口文档

接口文档就是对接口的说明书。它告诉我们：这个接口是做什么的、怎么请求、需要传哪些参数、会返回什么结果、有哪些错误情况。

站在测试人员角度，接口文档非常重要。因为我们做接口测试时，不能只靠猜接口怎么用，而是要根据接口文档去设计测试用例、准备测试数据、发送请求、检查响应结果。

### 接口文档是谁提供的？

通常由后端开发提供。

因为接口一般是后端开发设计和实现的，所以后端最清楚：

- 接口地址是什么
- 请求方法是什么
- 需要哪些参数
- 参数类型是什么
- 哪些参数必填
- 返回数据结构是什么
- 错误码有哪些
- 是否需要登录或权限

但在实际项目中，接口文档可能由不同角色一起维护：

| 角色 | 可能负责的内容 |
| --- | --- |
| 后端开发 | 编写接口地址、参数、返回值、错误码 |
| 前端开发 | 根据接口文档调用接口，也可能补充前端需要的字段 |
| 测试人员 | 根据文档设计测试用例，并发现文档不清楚或不一致的问题 |
| 产品经理 | 说明业务规则，比如登录失败提示、订单状态含义 |
| 项目负责人 | 推动接口文档及时更新 |

测试人员要注意：接口文档不一定永远正确。接口测试时如果发现实际返回和文档不一致，要及时和开发确认，是接口有 bug，还是文档没有更新。

### 接口文档是什么？

接口文档可以理解为接口测试的“需求说明书”。

一份比较完整的接口文档，通常包含：

- 接口名称：这个接口是做什么的
- 接口地址：请求 URL
- 请求方法：GET、POST、PUT、DELETE 等
- 请求头：比如 `Content-Type`、`Authorization`
- 请求参数：传哪些字段，字段类型是什么
- 参数说明：字段含义、是否必填、长度限制、取值范围
- 请求示例：给一个可以参考的请求数据
- 响应示例：接口成功时返回什么
- 错误示例：接口失败时返回什么
- 状态码或业务码：比如 `code=0` 表示成功
- 鉴权要求：是否需要登录、token、权限
- 业务规则：比如密码错误 5 次后锁定账号

测试人员看接口文档时，不能只看“怎么调通接口”，还要看“怎么测出问题”。

### 接口文档的常见方式

实际工作中，接口文档可能有很多形式。

| 方式 | 说明 |
| --- | --- |
| Word / Excel 文档 | 比较传统，适合简单项目，但更新不方便 |
| Markdown 文档 | 程序员常用，方便写接口说明 |
| Swagger / Knife4j | 常见的在线接口文档，可以直接查看接口、参数、响应 |
| Postman Collection | 可以把接口集合导入 Postman，直接调试 |
| Apifox / Apipost | 专门的接口管理平台，支持文档、调试、Mock、测试 |
| 后端代码注解生成 | 根据后端代码自动生成接口文档 |
| 项目 Wiki / 禅道 / Confluence | 团队统一维护接口说明 |

常见情况：

- 中小项目可能直接用 Apifox、Apipost
- Java 项目中 Swagger、Knife4j 很常见
- 测试人员使用 Postman 时，经常会导入接口集合或根据文档手动创建请求

#### 登录凭证 token 怎么理解？

很多初学者会误以为有两个登录接口：一个普通登录接口，一个带 token 的登录接口。

更准确的理解是：

1. 第一次登录时，用户还没有 token

   所以登录接口一般只需要传账号和密码。服务器验证账号密码正确后，会返回一个 token。

2. 登录成功后，token 就相当于“登录凭证”

   后续再访问购物车、订单、个人信息这些需要登录的接口时，就不用每次都传账号密码了，而是带上 token。

3. 服务器通过 token 判断当前用户是谁

   如果 token 正确，说明用户已经登录；如果 token 缺失、错误或过期，说明用户未登录或登录失效。

可以简单理解：

- 账号密码：用来换取 token
- token：用来证明“我已经登录过”

常见流程：

```text
1. 调用登录接口，传 username 和 password
2. 登录成功，服务器返回 token
3. Postman 保存这个 token
4. 请求购物车、订单、个人信息等接口时，在 Header 里带上 token
5. 服务器识别 token，返回当前用户的数据
```

例如登录成功后返回：

```json
{
  "code": 0,
  "message": "登录成功",
  "data": {
    "token": "token123"
  }
}
```

后续请求需要登录的接口时，Header 里这样传：

```http
Authorization: Bearer token123
```

注意：`Bearer token123` 是一种常见写法，意思是“我携带的登录凭证是 token123”。不同项目写法可能不一样，有些项目可能直接写 token，有些项目可能用 Cookie，有些项目可能请求头名字叫 `X-Token`。



#### 常见登录凭证形式：token、jwt_token、Cookie、Session

不同项目保存登录状态的方式不完全一样，但目的都是一样的：让服务器知道“当前请求是谁发的”。

初学者可以先这样理解：

| 名称 | 简单理解 | 常见传递位置 |
| --- | --- | --- |
| token | 一串登录凭证 | Header、Params、Body |
| jwt_token | 一种特殊格式的 token | Header 最常见 |
| Cookie | 浏览器自动保存和携带的一小段数据 | Cookie |
| Session | 服务器保存的登录会话 | 通常配合 Cookie 使用 |

##### 1. 普通 token

普通 token 就是一串登录凭证，可能长这样：

```text
43a2d8e33a7b439c83faabcd4919abdd
```

登录成功后，服务器返回 token：

```json
{
  "code": 0,
  "message": "登录成功",
  "data": {
    "token": "43a2d8e33a7b439c83faabcd4919abdd"
  }
}
```

后续请求时，可能这样传：

```http
Authorization: 43a2d8e33a7b439c83faabcd4919abdd
```

也可能这样传：

```http
X-Token: 43a2d8e33a7b439c83faabcd4919abdd
```

测试人员要看接口文档要求，不同项目请求头名字可能不一样。

##### 2. jwt_token

JWT 全称是 JSON Web Token。它也是 token 的一种，只是格式更特殊。

JWT 通常长得比较长，中间有两个点，分成三段：

```text
xxxxx.yyyyy.zzzzz
```

真实项目里可能类似这样：

```text
eyJhbGciOiJIUzI1NiJ9.eyJ1c2VySWQiOjEwMDF9.abc123signature
```

初学者不用一开始就研究 JWT 的加密细节，只要先记住：

- jwt_token 是一种 token
- 它通常由三段组成，中间用 `.` 分隔
- 它里面可能包含用户 ID、过期时间等信息
- 它一般放在 Header 里传给服务器

常见写法：

```http
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.eyJ1c2VySWQiOjEwMDF9.abc123signature
```

有些接口文档会把字段名写成：

```json
{
  "jwt_token": "eyJhbGciOiJIUzI1NiJ9.eyJ1c2VySWQiOjEwMDF9.abc123signature"
}
```

这时后续请求依然可能是放到 Header 里：

```http
Authorization: Bearer {{jwt_token}}
```

在 Postman 中，常见做法是把登录接口返回的 `jwt_token` 保存成环境变量，然后其他接口直接引用。

##### 3. Cookie

Cookie 是浏览器常用的一种保存登录状态的方式。

它的流程通常是：

```text
1. 用户登录成功
2. 服务器在响应头里返回 Set-Cookie
3. 浏览器保存 Cookie
4. 后续请求同一个网站时，浏览器自动带上 Cookie
5. 服务器根据 Cookie 判断用户是否登录
```

登录成功响应头可能长这样：

```http
Set-Cookie: sessionId=abc123; Path=/; HttpOnly
```

后续请求时，客户端会带上：

```http
Cookie: sessionId=abc123
```

在 Postman 里，也可以手动添加 Cookie，或者使用 Postman 自带的 Cookies 管理功能。

测试人员要注意：

- Cookie 是否登录成功后正确返回
- 后续请求是否自动带上 Cookie
- 删除 Cookie 后是否变成未登录
- Cookie 过期后是否需要重新登录
- 退出登录后 Cookie 是否失效

##### 4. Session

Session 通常和 Cookie 一起出现。

可以这样理解：

- Cookie 保存在客户端，比如浏览器或 Postman
- Session 保存在服务器
- Cookie 里通常保存一个 sessionId
- 服务器根据 sessionId 找到对应的 Session，判断用户是谁

举个简单例子：

```text
客户端 Cookie：sessionId=abc123
服务器 Session：abc123 对应用户 test001
```

当客户端请求购物车接口时：

```http
GET /api/cart/items HTTP/1.1
Host: example.com
Cookie: sessionId=abc123
```

服务器看到 `sessionId=abc123`，就知道当前用户是 `test001`，然后返回这个用户的购物车。

##### 5. token 和 Cookie 的区别

| 对比点 | token / jwt_token | Cookie / Session |
| --- | --- | --- |
| 常见位置 | Header 中较常见 | Cookie 中 |
| 常见场景 | App、前后端分离项目、小程序 | 传统 Web 网站 |
| 是否自动携带 | 通常需要前端或工具主动带上 | 浏览器通常会自动携带 |
| Postman 使用 | 常在 Headers 或 Authorization 中配置 | 可以在 Cookies 中管理 |
| 测试重点 | token 缺失、错误、过期、篡改 | Cookie 缺失、过期、退出后失效 |

不用死记哪个更高级，测试时最重要的是看接口文档：

- 登录成功后返回的是 token、jwt_token，还是 Set-Cookie？
- 后续接口要求把凭证放在哪里？
- Header 名字是什么？
- 是否需要加 `Bearer`？
- 凭证多久过期？
- 退出登录后凭证是否失效？

##### 6. Postman 里怎么处理这些登录凭证？

如果是 token 或 jwt_token：

1. 先调用登录接口
2. 从响应体里复制 token
3. 打开需要登录的接口
4. 在 Headers 里添加：

```http
Authorization: Bearer token值
```

或者：

```http
X-Token: token值
```

如果是 Cookie：

1. 先调用登录接口
2. 查看响应头是否有 `Set-Cookie`
3. Postman 通常会保存 Cookie
4. 再请求需要登录的接口
5. 检查请求里是否带上了 Cookie

##### 7. 测试人员常见测试点

无论项目用 token、jwt_token，还是 Cookie，测试思路都类似。

| 测试点 | 用例示例 | 预期结果 |
| --- | --- | --- |
| 正确凭证 | 带正确 token 或 Cookie 请求 | 请求成功 |
| 不带凭证 | 不传 token / Cookie | 返回未登录 |
| 错误凭证 | 随便写一个 token / Cookie | 返回认证失败 |
| 过期凭证 | 使用过期 token / Cookie | 返回登录过期 |
| 篡改凭证 | 修改 token 中的几个字符 | 返回认证失败 |
| 退出登录 | 退出后继续用原凭证请求 | 应该失效 |
| 用户隔离 | 用 A 用户凭证请求 | 只能看到 A 用户自己的数据 |
| 权限控制 | 普通用户访问管理员接口 | 返回无权限 |

一句话记住：

登录凭证不管叫什么，token、jwt_token、Cookie，本质上都是为了证明“我是谁、我是否登录、我有没有权限”。

#### 补充接口：获取当前登录用户信息

有些项目会提供一个“获取当前登录用户信息”的接口，用来校验 token 是否有效，也可以用来获取当前登录用户资料。

这个接口不是登录接口，而是“带 token 查询当前登录用户”的接口。

| 项目 | 内容 |
| --- | --- |
| 接口名称 | 获取当前登录用户信息 |
| 接口说明 | 根据 token 查询当前登录用户的信息 |
| 请求方法 | GET |
| 请求地址 | `/api/user/profile` |
| 是否需要登录 | 是 |
| 请求数据格式 | 无请求体 |
| 响应数据格式 | JSON |

请求头 Headers：

| 参数名 | 是否必填 | 示例 | 说明 |
| --- | --- | --- | --- |
| `Authorization` | 是 | `Bearer token123` | 登录凭证 |

请求示例：

```http
GET /api/user/profile HTTP/1.1
Host: example.com
Authorization: Bearer token123
```

成功响应示例：

```json
{
  "code": 0,
  "message": "查询成功",
  "data": {
    "userId": 1001,
    "username": "test001",
    "nickname": "测试用户",
    "mobile": "13800138000"
  }
}
```

未传 token 或 token 无效：

```json
{
  "code": 401,
  "message": "请先登录",
  "data": null
}
```

测试人员可以这样区分：

| 接口 | 是否传账号密码 | 是否传 token | 作用 |
| --- | --- | --- | --- |
| 登录接口 `/api/login` | 是 | 否 | 用账号密码登录，获取 token |
| 当前用户信息 `/api/user/profile` | 否 | 是 | 用 token 查询当前登录用户 |
| 购物车列表 `/api/cart/items` | 否 | 是 | 用 token 查询当前用户购物车 |

所以，不是所有带 token 的接口都叫登录接口。登录接口负责“发 token”，其他需要登录的接口负责“验证 token 并返回用户相关数据”。

### 接口文档举例：购物车商品列表接口

购物车商品列表接口和登录接口不一样，它通常需要用户先登录。

因为购物车数据是属于某个用户的，服务器必须知道“当前是谁在查询购物车”。所以请求这个接口时，一般要在请求头里携带登录后获得的 token。

#### 基本信息

| 项目 | 内容 |
| --- | --- |
| 接口名称 | 查询购物车商品列表 |
| 接口说明 | 查询当前登录用户购物车中的商品 |
| 请求方法 | GET |
| 请求地址 | `/api/cart/items` |
| 是否需要登录 | 是 |
| 请求数据格式 | 无请求体 |
| 响应数据格式 | JSON |

#### 请求头 Headers

| 参数名 | 是否必填 | 示例 | 说明 |
| --- | --- | --- | --- |
| `Authorization` | 是 | `Bearer token123` | 登录凭证，用来识别当前用户 |
| `Content-Type` | 否 | `application/json` | GET 请求通常没有 Body，可以不传 |

重点注意：

- `Authorization` 是这个接口的关键
- 没有 token，服务器不知道是谁在查购物车
- token 错误、过期、被篡改时，接口应该返回未登录或认证失败

#### 请求参数 Params

购物车列表接口有时不需要参数，直接查询当前登录用户的购物车。

如果支持分页，可能会有这些参数：

| 参数名 | 类型 | 是否必填 | 示例 | 说明 |
| --- | --- | --- | --- | --- |
| `page` | number | 否 | `1` | 当前页码，默认第 1 页 |
| `size` | number | 否 | `10` | 每页数量，默认 10 条 |

请求示例：

```http
GET /api/cart/items?page=1&size=10 HTTP/1.1
Host: example.com
Authorization: Bearer token123
```

在 Postman 中可以这样填写：

- Method 选择 `GET`
- URL 填写 `https://example.com/api/cart/items`
- Params 中填写 `page=1`、`size=10`
- Headers 中填写 `Authorization: Bearer token123`
- Body 选择 `none`

#### 测试人员重点关注什么？

这个接口是需要登录信息的，所以测试重点不只是“能不能返回购物车列表”，还要重点测鉴权。

可以设计这些测试用例：

| 测试点 | 用例示例 | 预期结果 |
| --- | --- | --- |
| 正常查询 | 携带正确 token 查询 | 返回当前用户的购物车列表 |
| 未登录 | 不传 `Authorization` | 返回请先登录 |
| token 错误 | 传一个随便写的 token | 返回认证失败 |
| token 过期 | 使用过期 token | 返回登录已过期 |
| token 被篡改 | 修改 token 中的部分字符 | 返回认证失败 |
| 用户隔离 | A 用户 token 查询 | 只能看到 A 用户自己的购物车 |
| 空购物车 | 已登录但购物车为空 | 返回空列表，而不是报错 |
| 分页正常 | `page=1&size=10` | 返回对应分页数据 |
| 分页异常 | `page=0` 或 `size=-1` | 返回分页参数错误 |
| 字段检查 | 检查商品名称、价格、数量、库存 | 字段完整，类型正确 |
| 敏感信息 | 查看响应是否返回用户密码等信息 | 不应该返回敏感信息 |

测试人员要特别注意“用户隔离”：

如果用 A 用户的 token 查询到了 B 用户的购物车，这就是很严重的问题。接口测试不能只看接口有没有返回数据，还要看返回的数据是不是属于当前登录用户。

### 测试人员拿到接口文档后要看什么？

测试人员拿到接口文档后，不要急着直接发请求，可以先检查这些内容：

1. 接口基本信息是否清楚

   比如接口名称、接口地址、请求方法、接口用途是否写明白。

2. 请求参数是否完整

   要看每个参数的字段名、类型、是否必填、默认值、长度限制、取值范围。

3. 请求头是否说明清楚

   比如是否需要 `Content-Type`，是否需要 `Authorization`，token 放在哪里。

4. 返回结果是否完整

   要看成功返回什么，失败返回什么，字段类型是什么，是否有响应示例。

5. 错误码是否明确

   比如参数错误、未登录、无权限、数据不存在分别返回什么。

6. 业务规则是否写清楚

   比如登录失败几次锁定账号、订单什么状态可以取消、优惠券是否过期。

7. 文档和实际接口是否一致

   如果文档写的是 POST，但实际只能 GET；或者文档写返回 `userName`，实际返回 `username`，都需要记录并反馈。

### 根据接口文档设计测试用例

以登录接口为例，可以从文档中提取测试点。

| 测试点 | 用例示例 | 预期结果 |
| --- | --- | --- |
| 正常场景 | 正确账号、正确密码 | 登录成功，返回 token |
| 必填校验 | 不传 username | 提示用户名不能为空 |
| 必填校验 | 不传 password | 提示密码不能为空 |
| 参数类型 | username 传数字 | 根据需求返回参数错误或正常转字符串 |
| 参数长度 | password 超过最大长度 | 返回参数错误 |
| 业务规则 | 密码错误 | 登录失败，不返回 token |
| 业务规则 | 冻结账号登录 | 提示账号被冻结 |
| 安全检查 | 响应中是否返回密码 | 不应该返回密码 |
| 请求头检查 | 不传 `Content-Type` | 可能返回参数格式错误 |
| 请求方法检查 | 用 GET 请求登录接口 | 返回方法不允许或接口不存在 |

所以接口文档不是只用来“照着发请求”的，它还能帮助我们设计正向用例、反向用例、边界用例、异常用例。

### 接口文档不清楚时怎么办？

实际工作里，经常会遇到接口文档写得不完整。

比如：

- 没写参数是否必填
- 没写字段类型
- 没写错误码
- 没写失败响应示例
- 没写是否需要登录
- 文档和实际返回不一致

测试人员可以这样处理：

- 先根据现有文档尝试调用接口
- 把不清楚的地方整理成问题
- 找后端开发或产品确认
- 确认后补充到测试用例或接口文档中
- 如果实际结果和文档不一致，要提交 bug 或让开发更新文档

常见沟通问题可以这样问：

- 这个参数是必填还是选填？
- 这个字段最大长度是多少？
- 这个接口是否需要 token？
- token 是放在 Header 里还是 Cookie 里？
- 密码错误时应该返回什么错误码？
- 用户不存在和密码错误是否要区分提示？
- 这个字段为空时应该返回 null、空字符串，还是不返回？









# 接口自动化测试

## 接口自动化测试用例设计思路与要点

接口自动化测试不是把手工接口用例简单复制到代码里，而是要选择适合长期回归、结果稳定、断言明确的接口场景进行自动化。

设计接口自动化用例时，可以按照下面的思路来分析：

1. 先明确测试目标

   接口自动化主要用于回归测试、冒烟测试、主流程验证、核心接口监控。

   例如登录、下单、支付回调、查询订单、修改用户信息等核心接口，适合优先自动化。

2. 根据接口文档拆分测试点

   从接口文档中提取请求地址、请求方式、请求头、请求参数、响应字段、错误码、业务规则等信息。

   每一个测试点都要能形成明确的输入和预期输出。

3. 优先覆盖核心业务流程

   自动化用例不是越多越好，要先覆盖稳定且重要的链路。

   比如电商系统可以先覆盖：

   - 登录
   - 查询商品
   - 加入购物车
   - 提交订单
   - 查询订单

4. 区分正向用例和反向用例

   正向用例主要验证接口在正常参数下是否能成功返回。

   反向用例主要验证接口在异常参数、缺少参数、权限不足、数据不存在等情况下是否能正确处理。

5. 明确断言内容

   接口自动化的重点不是“请求能发出去”，而是“结果是否符合预期”。

   常见断言包括：

   - 状态码断言：如 `200`、`401`、`403`、`404`、`500`
   - 业务码断言：如 `code = 0`、`code = 10001`
   - 响应字段断言：如返回中必须包含 `token`、`userId`
   - 字段类型断言：如 `id` 是数字，`name` 是字符串
   - 字段值断言：如用户名、订单状态、商品数量是否正确
   - 数据库断言：如下单成功后数据库是否新增订单记录
   - 业务规则断言：如未登录不能访问个人信息接口

6. 处理接口依赖关系

   很多接口不是独立存在的，后一个接口可能依赖前一个接口的返回值。

   例如：

   - 登录接口返回 `token`
   - 查询用户信息接口需要带上 `token`
   - 创建订单接口需要商品 `id`
   - 支付接口需要订单 `orderId`

   所以自动化脚本中要能提取上一个接口的响应数据，并传给后续接口使用。

7. 设计测试数据

   自动化用例要尽量保证数据可重复执行。

   常见做法：

   - 使用固定测试账号
   - 执行前准备测试数据
   - 执行后清理测试数据
   - 使用随机数、时间戳避免数据重复
   - 将测试数据放到 Excel、YAML、JSON 或数据库中统一维护

8. 注意环境和配置

   接口自动化通常会在不同环境执行，比如测试环境、预发布环境、生产监控环境。

   所以请求地址、账号、密码、数据库连接、请求头等配置不要写死在脚本里，应该统一放到配置文件中。

9. 关注用例稳定性

   自动化用例最怕不稳定。

   容易导致用例不稳定的原因有：

   - 测试数据被别人修改
   - 接口依赖第三方服务
   - 环境不稳定
   - 断言写得太模糊
   - 用例之间强依赖但执行顺序混乱
   - 执行后没有清理脏数据

10. 设计用例优先级

    可以按照接口重要程度和风险来划分优先级。

    - P0：核心主流程，冒烟测试必须执行
    - P1：重要功能和常见异常场景
    - P2：边界值、兼容性、低频异常场景
    - P3：补充场景或低风险场景

### 接口自动化用例常见字段

接口自动化用例一般可以包含下面这些字段：

| 字段 | 说明 |
| --- | --- |
| 用例编号 | 用来唯一标识一条用例，如 `API_LOGIN_001` |
| 用例标题 | 简要说明这条用例验证什么 |
| 接口模块 | 如登录、用户、商品、订单、支付 |
| 接口地址 | 请求的 URL 或路径 |
| 请求方式 | 如 GET、POST、PUT、DELETE |
| 是否需要登录 | 是否需要 token、Cookie 或其他鉴权信息 |
| 请求头 | 如 `Content-Type`、`Authorization` |
| 前置条件 | 执行该用例前需要满足的条件 |
| 请求参数 | Query、Path、Body 中的参数 |
| 依赖数据 | 是否依赖其他接口返回值 |
| 预期状态码 | HTTP 状态码预期结果 |
| 预期业务码 | 响应体中的业务 code |
| 断言内容 | 要检查哪些响应字段或业务结果 |
| 数据库校验 | 是否需要检查数据库数据 |
| 优先级 | P0、P1、P2、P3 |
| 是否自动化 | 是否纳入自动化执行 |
| 备注 | 特殊说明 |

### 接口自动化用例设计示例

以登录接口为例：

| 编号 | 标题 | 接口类别 | 请求地址 | 请求方式 | 是否需要登录 | 请求参数 | 预期结果 | 断言点 | 优先级 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| API_LOGIN_001 | 正确账号密码登录成功 | 登录 | `/api/login` | POST | 否 | `username=zhangsan`，`password=123456` | 登录成功，返回 token | 状态码为 200；`code=0`；返回 `token` | P0 |
| API_LOGIN_002 | 用户名为空登录失败 | 登录 | `/api/login` | POST | 否 | `username=`，`password=123456` | 提示用户名不能为空 | 状态码为 200 或 400；业务码符合文档；错误信息正确 | P1 |
| API_LOGIN_003 | 密码为空登录失败 | 登录 | `/api/login` | POST | 否 | `username=zhangsan`，`password=` | 提示密码不能为空 | 业务码符合文档；不返回 `token` | P1 |

### 设计接口自动化用例时的注意事项

1. 不建议一开始就把所有接口都自动化

   应该先从稳定、核心、重复执行频率高的接口开始。

2. 不要只断言状态码

   有些接口即使业务失败，HTTP 状态码也可能是 `200`，所以还要断言业务码、响应字段和业务数据。

3. 用例之间尽量降低依赖

   如果依赖太多，前面一条失败可能导致后面一批用例都失败。

4. 测试数据要可控

   自动化执行前要知道使用什么数据，执行后要知道是否需要清理数据。

5. 失败结果要容易定位

   自动化报告中应该能看到请求地址、请求参数、响应结果、断言失败原因。

6. 和接口文档保持一致

   如果自动化结果和接口文档不一致，要判断是接口 bug、文档问题，还是自动化脚本问题。

7. 接口自动化要持续维护

   接口字段、业务规则、错误码变化后，用例和断言也要同步更新。

总结：接口自动化测试用例设计的核心是“选对接口、准备数据、明确断言、处理依赖、保证稳定”。自动化不是为了追求数量，而是为了让核心接口在每次迭代后都能快速、稳定地完成回归验证。





## Excel接口测试用例访问

接口自动化中，Excel 常用来维护接口测试用例和测试数据。它的优点是直观、容易编辑、适合初学和中小型项目。

常见思路是：把每一行当成一条测试用例，把每一列当成用例字段，Python 读取 Excel 后循环执行接口请求。

### Excel 用例字段示例

| case_id | title | method | url | headers | params | body | expected_status | expected_code | check_field | priority | run |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| API_LOGIN_001 | 正确账号密码登录成功 | POST | `/api/login` | `{"Content-Type":"application/json"}` |  | `{"username":"zhangsan","password":"123456"}` | 200 | 0 | token | P0 | yes |
| API_LOGIN_002 | 密码错误登录失败 | POST | `/api/login` | `{"Content-Type":"application/json"}` |  | `{"username":"zhangsan","password":"error123"}` | 200 | 10001 | message | P1 | yes |

字段说明：

- `case_id`：用例编号，建议唯一
- `title`：用例标题
- `method`：请求方式，如 GET、POST、PUT、DELETE
- `url`：接口地址，可以是完整地址，也可以是接口路径
- `headers`：请求头，通常用 JSON 字符串保存
- `params`：GET 请求参数，通常用 JSON 字符串保存
- `body`：POST 请求体，通常用 JSON 字符串保存
- `expected_status`：预期 HTTP 状态码
- `expected_code`：预期业务 code
- `check_field`：需要检查的响应字段
- `priority`：用例优先级
- `run`：是否执行，`yes` 表示执行，`no` 表示跳过

### Python 使用 Pandas 读取 Excel

安装依赖：

```bash
pip install pandas openpyxl requests
```

读取 Excel 用例：

```python
import json
import pandas as pd


def parse_json_cell(value):
    """把 Excel 单元格中的 JSON 字符串转成 Python 字典。"""
    if pd.isna(value) or value == "":
        return {}
    return json.loads(value)


cases = pd.read_excel("api_cases.xlsx", sheet_name="login")

for _, case in cases.iterrows():
    if str(case["run"]).lower() != "yes":
        continue

    case_id = case["case_id"]
    title = case["title"]
    method = case["method"].upper()
    url = "http://test.example.com" + case["url"]
    headers = parse_json_cell(case["headers"])
    params = parse_json_cell(case["params"])
    body = parse_json_cell(case["body"])

    print(case_id, title, method, url)
```



使用 Excel 管理接口测试用例时要注意：

- 字段名尽量使用英文，方便 Python 读取和维护
- JSON 字符串要写成标准格式，双引号不能省略
- 不同模块可以放在不同 Sheet 中，如 `login`、`order`、`product`
- 敏感信息不要直接写在 Excel 中，可以放到配置文件或环境变量中
- Excel 适合用例数量不太大、协作人员不太多的项目











## MySQL数据库接口测试用例访问

当接口用例数量越来越多，或者需要多人协作、统一管理、按条件查询时，可以把接口测试用例放到 MySQL 数据库中。

相比 Excel，MySQL 管理接口测试用例有这些特点：

| 对比项 | Excel | MySQL |
| --- | --- | --- |
| 使用难度 | 简单，适合初学 | 需要建表和 SQL 基础 |
| 数据量 | 适合少量用例 | 适合大量用例 |
| 多人协作 | 容易冲突 | 更适合多人维护 |
| 查询能力 | 筛选能力有限 | 可以按模块、优先级、是否执行等条件查询 |
| 数据规范 | 容易手误 | 可以通过字段类型、约束控制 |
| 版本管理 | 不方便 | 可以配合平台或脚本管理 |
| 维护成本 | 前期低，后期高 | 前期高，后期更稳定 |

所以 Excel 更适合学习、演示、小项目；MySQL 更适合公司内部平台化、用例数量较多、需要长期维护的接口自动化项目。

### MySQL 用例表设计示例

接口测试用例表字段建议使用英文，方便 Python、SQL、接口平台统一处理。

```sql
CREATE TABLE api_test_case (
    id INT PRIMARY KEY AUTO_INCREMENT,
    case_id VARCHAR(50) NOT NULL UNIQUE,
    title VARCHAR(200) NOT NULL,
    module VARCHAR(50),

    url VARCHAR(255) NOT NULL,
    headers TEXT,
    params TEXT,
    body TEXT,
    expected_status INT,
    expected_code INT,
    check_field VARCHAR(100),
    priority VARCHAR(10),
    run_flag TINYINT DEFAULT 1,
    remark VARCHAR(255),
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);
```

### Python 使用 PyMySQL 读取 MySQL 用例

读取数据库中的接口用例：

```python
import pymysql


connection = pymysql.connect(
    host="127.0.0.1",
    port=3306,
    user="root",
    password="123456",
    database="test_platform",
    charset="utf8mb4",
    cursorclass=pymysql.cursors.DictCursor
)

sql = """
SELECT case_id, title, module, method, url, headers, params, body,
       expected_status, expected_code, check_field, priority
FROM api_test_case
WHERE run_flag = 1
ORDER BY id ASC
"""

try:
    with connection.cursor() as cursor:
        cursor.execute(sql)
        cases = cursor.fetchall()

    for case in cases:
        print(case["case_id"], case["title"], case["method"], case["url"])
finally:
    connection.close()
```

### 用例管理思路

实际项目中可以这样管理接口自动化用例：

1. 初期用 Excel 设计和评审测试用例

   Excel 更直观，方便测试、开发、产品一起确认字段和场景。

2. 用例稳定后导入 MySQL

   把 Excel 中的字段映射到数据库字段，比如 `case_id`、`title`、`method`、`url`、`body`、`expected_code`。

3. 自动化脚本统一从 MySQL 读取用例

   脚本不关心用例写在哪里，只负责读取数据、发送请求、执行断言、生成报告。

4. 后续可以做成接口测试平台

   在页面上新增、编辑、禁用、执行测试用例，底层仍然可以用 MySQL 保存数据。

总结：Excel 适合“写用例和学习”，MySQL 适合“统一管理和长期维护”。接口自动化框架真正要做到的是数据和代码分离，让测试数据可以独立维护，让执行逻辑保持稳定。











## ⭐PyTest自动化测试框架

PyTest 是 Python 中常用的自动化测试框架，适合做单元测试、自动化测试脚本管理等。

它的特点：

- 写法简单，普通函数就可以作为测试用例
- 使用 `assert` 直接断言
- 支持参数化，可以一条测试逻辑跑多组数据
- 插件丰富，可以生成测试报告、控制用例执行顺序、失败重跑等

在自动化测试中，PyTest 常用来组织测试用例、执行断言、管理测试数据、生成测试报告。

### PyTest 使用约束

PyTest 对文件名、类名、函数名有一定命名规则，符合规则的用例才会被自动收集。

常见约束：

- 测试文件名一般以 `test_` 开头，或以 `_test.py` 结尾
- 测试函数名必须以 `test_` 开头
- 测试类名必须以 `Test` 开头，测试类中不要写 `__init__` 方法
- 测试类中的测试方法必须以 `test_` 开头
- 普通工具函数不要以 `test_` 开头，否则可能被当成测试用例执行

示例：

```python
class TestLogin:
    def test_login_success(self):
        assert True

    def test_login_fail(self):
        assert 1 == 1
```

下面这种写法不会被 PyTest 当成测试用例：

```python
def login_success():
    assert True


class LoginTest:
    def login_fail(self):
        assert True
```

原因是函数名没有以 `test_` 开头，类名也没有以 `Test` 开头。



### PyTest 断言

PyTest 直接使用 Python 的 `assert` 进行断言。

常见断言写法：

```python
def test_assert_demo():
    status_code = 200
    result = {
        "code": 0,
        "message": "success",
        "data": {
            "token": "abc123",
            "user_id": 1001
        }
    }

    assert status_code == 200
    assert result["code"] == 0
    assert result["message"] == "success"
    assert "token" in result["data"]
    assert result["data"]["user_id"] == 1001
```



带错误提示的断言：

```python
def test_login_code():
    result = {"code": 10001, "message": "密码错误"}

    assert result["code"] == 0, "登录接口业务码不符合预期"
```

断言失败后，PyTest 会显示失败位置、实际结果和预期结果，方便定位问题。



### PyTest 参数化

参数化可以用一段测试代码执行多组测试数据，适合接口自动化中的正向、反向、边界值场景。

使用 `@pytest.mark.parametrize` 实现参数化。

简单示例：

```python
import pytest


@pytest.mark.parametrize(
    "username,password,expected_code",
    [
        ("zhangsan", "123456", 0),
        ("zhangsan", "error123", 10001),
        ("", "123456", 10002),
        ("zhangsan", "", 10003),
    ]
)
def test_login(username, password, expected_code):
    result = login(username, password)

    assert result["code"] == expected_code


def login(username, password):
    if username == "":
        return {"code": 10002, "message": "用户名不能为空"}
    if password == "":
        return {"code": 10003, "message": "密码不能为空"}
    if password != "123456":
        return {"code": 10001, "message": "密码错误"}
    return {"code": 0, "message": "登录成功"}
```





### 测试用例组织管理

默认执行顺序一般为：

1. 先按文件名顺序收集测试文件

   例如 `test_01_login.py` 通常会比 `test_02_order.py` 先执行。

2. 同一个文件中，按代码从上到下的顺序执行测试函数和测试类

3. 同一个测试类中，按方法定义顺序执行测试方法

示例：

```python
def test_01_login():
    print("登录")


def test_02_query():
    print("查询")


class TestUser:
    def test_03_add_user(self):
        print("新增用户")

    def test_04_delete_user(self):
        print("删除用户")
```

执行时通常是：

```text
test_01_login
test_02_query
test_03_add_user
test_04_delete_user
```

注意：不要过度依赖默认执行顺序。测试用例最好能独立运行，如果强依赖顺序，后期维护会比较麻烦。

**前置与后置操作**

前置操作是指测试用例执行前要做的事情，后置操作是指测试用例执行后要做的事情。

比如：

- 执行前准备测试数据
- 执行前打印日志
- 执行前初始化对象
- 执行后清理测试数据
- 执行后释放资源

1、函数级别：setup_function 和 teardown_function

如果测试用例是普通函数，可以使用 `setup_function` 和 `teardown_function`。

```python
def setup_function():
    print("每个测试函数执行前执行")


def teardown_function():
    print("每个测试函数执行后执行")


def test_add():
    print("执行 test_add")
    assert 1 + 1 == 2


def test_sub():
    print("执行 test_sub")
    assert 3 - 1 == 2
```

执行顺序：

```text
setup_function
test_add
teardown_function
setup_function
test_sub
teardown_function
```

2、模块级别：setup_module 和 teardown_module

`setup_module` 在当前测试文件执行前执行一次，`teardown_module` 在当前测试文件执行后执行一次。

```python
def setup_module():
    print("当前模块执行前执行一次")


def teardown_module():
    print("当前模块执行后执行一次")


def test_case_01():
    print("执行 test_case_01")
    assert True


def test_case_02():
    print("执行 test_case_02")
    assert True
```

执行顺序：

```text
setup_module
test_case_01
test_case_02
teardown_module
```

3、类级别：setup_class 和 teardown_class

如果测试用例写在类中，可以使用 `setup_class` 和 `teardown_class`。

```python
class TestUser:
    def setup_class(self):
        print("测试类执行前执行一次")

    def teardown_class(self):
        print("测试类执行后执行一次")

    def test_add_user(self):
        print("执行 test_add_user")
        assert True

    def test_delete_user(self):
        print("执行 test_delete_user")
        assert True
```

执行顺序：

```text
setup_class
test_add_user
test_delete_user
teardown_class
```

4、方法级别：setup_method 和 teardown_method

`setup_method` 和 `teardown_method` 会在类中的每个测试方法前后执行。

```python
class TestLogin:
    def setup_method(self):
        print("每个测试方法执行前执行")

    def teardown_method(self):
        print("每个测试方法执行后执行")

    def test_login_success(self):
        print("执行 test_login_success")
        assert True

    def test_login_fail(self):
        print("执行 test_login_fail")
        assert True
```

执行顺序：

```text
setup_method
test_login_success
teardown_method
setup_method
test_login_fail
teardown_method
```
