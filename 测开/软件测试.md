# 接口测试

## 什么是接口？

接口可以理解为“两个系统、两个模块之间沟通的通道”。

在软件里，一个功能通常不是单独完成的，而是由前端页面、后端服务、数据库、第三方系统等一起配合完成。它们之间传递数据、请求服务的入口，就叫接口。

举个例子：

我们在登录页面输入账号和密码，点击“登录”按钮。页面本身不会判断账号密码是否正确，它会把账号和密码发送给后端的登录接口。后端接口收到数据后，会去判断账号密码是否正确，然后返回结果。

比如登录接口可以简单理解为：

- 请求地址：`/api/login`
- 请求数据：账号、密码
- 返回结果：登录成功、登录失败、用户信息、登录凭证等

所以，接口的本质就是：一方按照约定发送数据，另一方按照约定处理并返回结果。





## 什么是接口测试，为什么要进行接口测试？

接口测试就是测试接口是否能按照约定正常工作。

测试时，我们不一定通过页面操作，而是直接向接口发送请求，然后检查接口返回的数据是否正确、状态是否正确、业务逻辑是否正确。

还是以登录接口为例，我们可以测试：

- 输入正确账号和密码，是否返回登录成功
- 输入错误密码，是否返回登录失败
- 不输入账号，是否提示账号不能为空
- 密码为空，是否提示密码不能为空
- 已冻结的账号，是否不能登录
- 返回结果中是否包含正确的用户信息

为什么要进行接口测试？

1. 接口是前后端交互的核心

   页面上的很多功能，背后都是接口在处理。比如登录、注册、下单、支付、查询订单等。如果接口出问题，页面功能也很可能出问题。

2. 可以更早发现问题

   有时候前端页面还没开发完，后端接口已经完成了。这时测试人员可以先测接口，不用等页面全部做好。

3. 测试更直接

   功能测试通常要点页面、填表单、点按钮。接口测试可以直接给接口传数据，检查返回结果，更容易定位问题是前端问题还是后端问题。

4. 可以覆盖一些页面不好操作的场景

   比如金额传负数、手机号格式错误、订单状态异常、用户权限不正确等。这些数据通过页面不一定容易构造，但接口测试可以直接发送这些特殊数据。

简单来说，接口测试就是绕过页面，直接检查系统内部的数据处理是否正确。





## 接口测试与功能测试的区别

功能测试主要站在用户角度，验证页面功能是否能正常使用；接口测试主要站在数据交互角度，验证接口的请求和响应是否正确。

举个例子：测试登录功能。

功能测试会这样测：

- 打开登录页面
- 输入账号和密码
- 点击登录按钮
- 观察是否跳转到首页
- 检查页面是否显示用户名

接口测试会这样测：

- 直接请求登录接口 `/api/login`
- 传入账号和密码
- 查看接口返回的状态码、返回数据、错误提示
- 检查登录成功时是否返回 token 或用户信息
- 检查登录失败时是否返回正确的错误信息

两者的区别可以这样理解：

| 对比点 | 功能测试 | 接口测试 |
| --- | --- | --- |
| 测试角度 | 从用户使用角度出发 | 从数据交互和业务逻辑角度出发 |
| 是否依赖页面 | 通常依赖页面 | 不一定依赖页面 |
| 测试方式 | 点页面、填数据、看结果 | 发请求、传参数、看响应 |
| 发现问题位置 | 发现页面或整体功能问题 | 更容易发现后端接口、数据处理问题 |
| 测试效率 | 手工操作较多，速度相对慢 | 可以直接构造数据，效率较高 |
| 适合阶段 | 页面完成后测试 | 接口完成后就可以测试 |

可以用一句话记住：

功能测试看“用户能不能正常用”，接口测试看“系统之间传数据和处理数据对不对”。









## ⭐HTTP协议

### 简介

HTTP 全称是 HyperText Transfer Protocol，中文叫“超文本传输协议”。

它是应用层协议，主要规定客户端和服务器之间如何传输数据。

请求 Request：客户端发给服务器，告诉服务器“我要什么、带了什么数据”；响应 Response：服务器返回给客户端，告诉客户端“处理结果是什么”。

常见应用场景：

- 浏览器访问网页，比如打开百度、京东、后台管理系统
- 前后端分离项目中，前端页面调用后端接口
- App 调用登录、注册、下单、支付等接口
- 第三方系统对接，比如支付回调、短信服务、物流查询
- 接口测试、接口自动化测试、性能测试中的请求发送

在接口测试里，常用 Postman、Apifox、JMeter 等工具发送 HTTP 请求，然后查看服务器返回的 HTTP 响应。

用户在 App 或网页上点击“登录”按钮，本质上可能就是客户端向服务器发送了一个 HTTP 请求；服务器处理完之后，再返回一个 HTTP 响应，告诉客户端登录成功还是失败。

HTTP 消息主要分为两类：

- HTTP 请求
- HTTP 响应



### HTTP 请求

HTTP 请求就是客户端发给服务器的一段消息，用来说明“我要访问哪个接口、用什么方式访问、带了哪些参数、我是谁、提交了什么数据”。

先看一个比较完整的 HTTP 请求报文。这个例子模拟用户在电商网站里查询自己的订单列表：

```http
GET /api/v1/orders?status=paid&page=1&pageSize=20&sort=createdAt_desc HTTP/1.1
Host: shop-api.example.com
Connection: keep-alive
Accept: application/json, text/plain, */*
Accept-Encoding: gzip, deflate, br
Accept-Language: zh-CN,zh;q=0.9,en;q=0.8
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.xxx.yyy
Cookie: Hm_lvt=1700000000; device_id=web_8f3a2c; session_id=sess_9a7b6c5d
Origin: https://www.example.com
Referer: https://www.example.com/account/orders
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/125.0.0.0 Safari/537.36 Edg/125.0.0.0
X-Requested-With: XMLHttpRequest
```

HTTP 请求报文一般可以分成 4 部分：

| 组成部分 | 在报文中的位置 | 作用 |
| --- | --- | --- |
| 请求行 Request Line | 第一行 | 说明请求方法、请求目标、HTTP 版本 |
| 请求头 Headers | 请求行下面的一组 `key: value` | 说明客户端信息、数据格式、登录凭证、来源、缓存等附加信息 |
| 空行 | 请求头和请求体之间 | 用来分隔请求头和请求体，哪怕没有请求体也会有这个分隔 |
| 请求体 Body | 空行后面 | 真正提交给服务器的数据，GET 通常没有，POST 经常有 |

如果是一个登录接口，POST 请求报文可能长这样：

```http
POST /api/v1/auth/login HTTP/1.1
Host: shop-api.example.com
Connection: keep-alive
Accept: application/json, text/plain, */*
Accept-Encoding: gzip, deflate, br
Accept-Language: zh-CN,zh;q=0.9,en;q=0.8
Content-Type: application/json;charset=UTF-8
Content-Length: 64
Origin: https://www.example.com
Referer: https://www.example.com/login
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/125.0.0.0 Safari/537.36 Edg/125.0.0.0

{
  "username": "test001",
  "password": "Test@123456"
}
```

注意：请求头结束后有一个空行，空行下面才是请求体。`Content-Type` 告诉服务器请求体是什么格式，`Content-Length` 表示请求体长度，很多工具会自动计算。

1、请求行 Request Line

请求行是 HTTP 请求报文的第一行，格式通常是：

```http
请求方法 请求目标 HTTP版本
```

例如：

```http
GET /api/v1/orders?status=paid&page=1&pageSize=20 HTTP/1.1
```

它可以拆成：

- `GET`：请求方法，表示这次想让服务器做什么
- `/api/v1/orders?status=paid&page=1&pageSize=20`：请求目标，包含接口路径和查询参数
- `HTTP/1.1`：HTTP 版本

在浏览器地址栏或 Postman 的 URL 输入框里，我们通常写完整 URL：

```text
https://shop-api.example.com/api/v1/orders?status=paid&page=1&pageSize=20
```

但在 HTTP/1.1 原始报文里，请求行通常只写路径和查询参数：

```http
GET /api/v1/orders?status=paid&page=1&pageSize=20 HTTP/1.1
Host: shop-api.example.com
```

也就是说，完整 URL 里的域名 `shop-api.example.com` 通常不会写在请求行里，而是放在请求头 `Host` 中。Postman、浏览器、Apifox 这类工具会帮我们把完整 URL 拆成“请求行 + Host 请求头”等底层报文内容。

2、请求方法 Method

请求方法表示客户端希望服务器执行什么操作。最常见的是 `GET` 和 `POST`。

| 方法 | 常见含义 | 常见场景 |
| --- | --- | --- |
| `GET` | 获取、查询数据 | 查询商品列表、订单列表、用户详情 |
| `POST` | 提交、新增或执行某个动作 | 登录、注册、创建订单、提交表单 |

`GET` 请求通常用于查询数据。比如：

```text
https://shop-api.example.com/api/v1/products?keyword=iPhone%2015&category=phone&page=1&pageSize=20
```

对应的 HTTP 报文可以写成：

```http
GET /api/v1/products?keyword=iPhone%2015&category=phone&page=1&pageSize=20 HTTP/1.1
Host: shop-api.example.com
Accept: application/json, text/plain, */*
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/125.0.0.0 Safari/537.36 Edg/125.0.0.0
```

`GET` 的特点：

- 参数经常拼在 URL 后面，方便复制、分享、收藏
- 一般没有请求体 Body
- 适合做查询，不适合提交密码、身份证号等敏感数据
- 参数会显示在浏览器地址栏、日志、抓包工具中，测试时要注意敏感信息泄露
- 如果接口文档写明 GET 参数在 Params 中，Postman 里可以直接填 Params 页签，工具会自动拼接到 URL 后面

`POST` 请求通常用于提交数据。比如登录：

```http
POST /api/v1/auth/login HTTP/1.1
Host: shop-api.example.com
Accept: application/json, text/plain, */*
Content-Type: application/json;charset=UTF-8
Origin: https://www.example.com
Referer: https://www.example.com/login

{
  "username": "test001",
  "password": "Test@123456"
}
```

`POST` 的特点：

- 提交的数据经常放在请求体 Body 中
- 适合登录、注册、新增、修改、下单、上传等场景
- Body 可以是 JSON、表单、文件、二进制等格式
- 如果 Body 是 JSON，请求头通常要带 `Content-Type: application/json`
- POST 也可以带 URL 参数，比如 `/api/v1/orders/submit?couponId=888`，同时 Body 里再放订单明细

3、请求地址 URL

URL 是接口的完整访问地址。一个真实一点的完整 URL 可以这样写：

```text
https://shop-api.example.com:443/api/v1/products/search?keyword=iPhone%2015&category=phone&page=1&pageSize=20&sort=price_asc#reviews
```

这个 URL 可以拆成：

| 部分 | 示例 | 说明 |
| --- | --- | --- |
| 协议 scheme | `https` | 使用什么协议访问，接口常见是 `http` 或 `https` |
| 域名 host | `shop-api.example.com` | 要访问哪台服务器，测试环境常见如 `test-api.xxx.com` |
| 端口 port | `443` | 服务器端口，`https` 默认 443，`http` 默认 80，默认端口常省略 |
| 路径 path | `/api/v1/products/search` | 接口路径，通常对应后端某个接口 |
| 查询参数 query | `keyword=iPhone%2015&category=phone&page=1&pageSize=20&sort=price_asc` | `?` 后面的参数，多个参数用 `&` 连接 |
| 片段 fragment | `#reviews` | `#` 后面的页面片段，主要给浏览器前端使用，通常不会发送给服务器 |

几个容易混淆的点：

- `?` 后面是查询参数 Query Params
- 多个查询参数用 `&` 连接
- 参数一般是 `key=value` 形式
- URL 中不能直接出现空格，所以 `iPhone 15` 会被编码成 `iPhone%2015`
- `#reviews` 这种片段标识不会进入 HTTP 请求报文，接口测试时一般不用关注

在 Postman 或浏览器里填的是完整 URL：

```text
https://shop-api.example.com/api/v1/products/search?keyword=iPhone%2015&page=1&pageSize=20
```

在 HTTP 报文里通常会变成：

```http
GET /api/v1/products/search?keyword=iPhone%2015&page=1&pageSize=20 HTTP/1.1
Host: shop-api.example.com
```

所以要区分两种写法：

| 场景 | 写法 | 例子 |
| --- | --- | --- |
| 浏览器地址栏 | 完整 URL | `https://shop-api.example.com/api/v1/products/search?keyword=iPhone%2015` |
| Postman URL 输入框 | 完整 URL | `https://shop-api.example.com/api/v1/products/search?keyword=iPhone%2015` |
| HTTP 原始报文请求行 | 路径 + 查询参数 | `GET /api/v1/products/search?keyword=iPhone%2015 HTTP/1.1` |
| HTTP 原始报文请求头 | 域名放在 `Host` | `Host: shop-api.example.com` |

4、请求参数 Params

请求参数是客户端传给服务器的数据。常见位置有 3 种：

| 参数位置 | 常见名称 | 例子 | 常见场景 |
| --- | --- | --- | --- |
| URL 路径中 | Path Params | `/api/v1/users/1001` 中的 `1001` | 根据 ID 查询详情、删除某条数据 |
| URL 问号后 | Query Params | `?page=1&pageSize=20` | 查询、筛选、分页、排序 |
| 请求体中 | Body | `{"username":"test001","password":"123456"}` | 登录、注册、新增、修改 |

Path Params 是路径的一部分：

```http
GET /api/v1/users/1001 HTTP/1.1
Host: shop-api.example.com
```

这里的 `1001` 通常表示用户 ID。

Query Params 放在 `?` 后面：

```text
?status=paid&page=1&pageSize=20&sort=createdAt_desc
```

含义：

- `status=paid`：只查已支付订单
- `page=1`：第 1 页
- `pageSize=20`：每页 20 条
- `sort=createdAt_desc`：按创建时间倒序

Body 参数放在请求体里：

```json
{
  "receiverName": "张三",
  "receiverPhone": "13800138000",
  "addressId": 9527,
  "items": [
    {
      "skuId": 30001,
      "quantity": 2
    }
  ]
}
```

接口测试时，参数要重点检查：

- 参数名是否和接口文档一致，比如 `pageSize` 不要写成 `pagesize`
- 参数类型是否正确，比如数字 `20` 不要误传成字符串 `"20"`
- 必填参数是否都传了
- 可选参数不传时是否有合理默认值
- 空字符串、`null`、超长字符串、特殊字符是否能正确处理
- 分页参数、排序参数、筛选参数组合后结果是否正确

5、请求头 Headers

请求头是客户端发送给服务器的附加信息，写法是 `请求头名称: 请求头值`。它不属于请求体，但会影响服务器如何解析请求、识别用户、判断来源和返回数据。

常见请求头：

| 请求头 | 作用 | 测试关注点 |
| --- | --- | --- |
| `Host` | 指定访问的域名和端口 | HTTP/1.1 必需；同一 IP 上可能根据 Host 区分不同站点 |
| `Accept` | 告诉服务器客户端希望接收的数据格式 | 接口常见值是 `application/json` |
| `Content-Type` | 告诉服务器请求体是什么格式 | Body 是 JSON 时通常是 `application/json;charset=UTF-8` |
| `Authorization` | 登录凭证、鉴权信息 | 常见写法是 `Bearer token`，重点测不传、错误、过期、越权 |
| `Cookie` | 携带浏览器保存的 Cookie | Cookie + Session 登录系统中很重要 |
| `Session` / `X-Session-Id` | 项目自定义的会话 ID 请求头 | 不是 HTTP 标准通用头；有些项目不用 Cookie，而是要求把 sessionId 放在 Header 里 |
| `User-Agent` | 标识浏览器、系统、设备、工具 | 兼容性、移动端 H5、风控场景可能关注 |
| `Origin` | 请求来源的源，包含协议、域名、端口 | 跨域请求中常见 |
| `Referer` | 当前请求从哪个页面发起 | 注意标准拼写是 `Referer`，不是 `Referrer` |
| `Accept-Language` | 客户端偏好的语言 | 国际化、多语言系统可能影响返回文案 |
| `Accept-Encoding` | 客户端支持的压缩方式 | 响应可能带 `Content-Encoding: gzip` |
| `Cache-Control` | 客户端缓存控制 | 页面或接口数据没更新时可以排查缓存 |
| `X-Requested-With` | 常用于标识 Ajax 请求 | 老项目里可能用 `XMLHttpRequest` 判断异步请求 |

`Authorization` 常见写法：

```http
Authorization: Bearer token123
```

含义是使用 Bearer Token 作为登录凭证。很多 JWT 登录接口都会这样传：

```http
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.xxx.yyy
```

也有项目不用标准的 `Authorization`，而是自定义一个请求头，例如：

```http
jwt_token: token123
```

测试时不要死记字段名，要以接口文档和实际系统为准。鉴权重点验证：

- 不传 token 是否返回未登录
- token 错误是否返回认证失败
- token 过期是否返回过期提示
- 普通用户 token 是否不能访问管理员接口
- A 用户 token 是否不能查看 B 用户的数据

`Content-Type` 和 Body 类型要对应：

| Body 类型 | Postman 里常见选择 | 常见 Content-Type |
| --- | --- | --- |
| 没有 Body | `none` | 通常不需要传 |
| JSON | `raw` + `JSON` | `application/json` |
| 普通表单 | `x-www-form-urlencoded` | `application/x-www-form-urlencoded` |
| 文件或混合表单 | `form-data` | `multipart/form-data` |
| 单个二进制文件 | `binary` | 按文件类型决定，如 `image/png` |



6、请求体 Body

请求体是真正提交给服务器的数据。不是所有请求都有 Body，GET 查询类请求通常没有 Body；POST 登录、新增、修改、上传类接口经常有 Body。

JSON 请求体示例：

```json
{
  "username": "test001",
  "password": "Test@123456"
}
```

表单请求体示例：

```text
username=test001&password=Test%40123456
```

Body 类型常见有：

| Body 类型 | 说明 | 常见场景 |
| --- | --- | --- |
| none | 没有请求体 | GET 查询 |
| raw JSON | 原始 JSON 数据 | 前后端分离接口、App 接口 |
| x-www-form-urlencoded | 普通表单键值对 | 传统表单提交 |
| form-data | 表单数据，可以上传文件 | 文件上传、带文件的表单 |
| binary | 二进制文件 | 上传单个文件 |

接口测试时，Body 要重点检查：

- 字段名是否正确
- 字段类型是否正确
- 必填字段是否都传了
- 多层 JSON、数组、对象结构是否符合文档
- 空值、`null`、超长字符串、特殊字符是否能正确处理
- JSON 格式是否正确，比如双引号、逗号、括号是否完整
- `Content-Type` 是否和 Body 类型一致



### HTTP 响应

HTTP 响应是服务器处理请求后返回给客户端的消息。

在 Postman 里发送请求后，下方看到的结果就是响应。测试人员要重点看：

- 状态码 Status Code
- 响应头 Headers
- 响应体 Body
- 响应时间 Time
- 响应大小 Size

1、状态行和状态码

响应的第一行叫状态行，表示服务器处理结果。

例子：

```http
HTTP/1.1 200 OK
```

含义：

- `HTTP/1.1`：HTTP 版本
- `200`：状态码
- `OK`：状态文本

状态码按开头数字可以分成 5 类：

| 分类 | 含义 | 常见理解 |
| --- | --- | --- |
| `1xx` | 信息响应 | 请求已收到，继续处理，接口测试中较少关注 |
| `2xx` | 成功 | 请求成功处理 |
| `3xx` | 重定向 | 需要跳转到其他地址 |
| `4xx` | 客户端错误 | 请求地址、参数、权限等有问题 |
| `5xx` | 服务端错误 | 服务器内部异常、网关异常、服务不可用 |

常见状态码：

| 状态码 | 含义 | 测试时怎么理解 |
| --- | --- | --- |
| `200 OK` | 请求成功 | 接口正常返回，最常见 |
| `201 Created` | 创建成功 | 新增用户、创建订单成功 |
| `204 No Content` | 成功但无响应体 | 删除成功但不返回内容 |
| `301 Moved Permanently` | 永久重定向 | 地址永久变更 |
| `302 Found` | 临时重定向 | 登录后跳转、临时跳转 |
| `304 Not Modified` | 资源未修改 | 命中缓存，浏览器可用本地缓存 |
| `400 Bad Request` | 请求错误 | 参数格式错误、缺少必填参数 |
| `401 Unauthorized` | 未认证 | 没登录、token 缺失、token 无效 |
| `403 Forbidden` | 无权限 | 已登录，但没有访问该资源的权限 |
| `404 Not Found` | 资源不存在 | URL 错误、接口不存在、数据不存在 |
| `405 Method Not Allowed` | 方法不允许 | 该接口不支持当前请求方法 |
| `409 Conflict` | 资源冲突 | 重复注册、重复提交、数据状态冲突 |
| `415 Unsupported Media Type` | 媒体类型不支持 | `Content-Type` 不正确 |
| `429 Too Many Requests` | 请求过多 | 触发限流 |
| `500 Internal Server Error` | 服务器内部错误 | 后端代码异常 |
| `502 Bad Gateway` | 网关错误 | 网关从上游服务拿到异常响应 |
| `503 Service Unavailable` | 服务不可用 | 服务停机、过载、维护中 |
| `504 Gateway Timeout` | 网关超时 | 后端服务响应太慢或无响应 |

注意：HTTP 状态码不等于业务结果。

有些项目登录失败也返回 `200`，但响应体中会有业务码：

```json
{
  "code": 10001,
  "message": "账号或密码错误",
  "success": false
}
```

所以接口测试时要同时看：

- HTTP 状态码
- 响应体中的业务 `code`
- 响应体中的 `message`
- 响应体中的业务数据



2、响应头 Headers

响应头 Headers 是服务器返回给客户端的附加信息。它会告诉客户端数据格式、缓存策略、Cookie 设置、跨域规则、重定向地址等。

常见响应头：

| 响应头 | 作用 | 测试关注点 |
| --- | --- | --- |
| `Content-Type` | 响应体格式 | 是否为接口文档要求的 `application/json`、`text/html`、文件类型等 |
| `Content-Length` | 响应体大小 | 下载文件、性能分析时可关注 |
| `Content-Encoding` | 响应压缩方式 | 如 `gzip`、`br`，与请求头 `Accept-Encoding` 对应 |
| **`Set-Cookie`** | 服务器要求客户端保存 Cookie | 登录后是否正确下发 Cookie，退出后是否失效 |
| `Cache-Control` | 服务器缓存策略 | 页面或接口是否允许缓存，缓存时间是否合理 |
| `Location` | 重定向目标地址 | `301`、`302` 时关注跳转是否正确 |
| `Access-Control-Allow-Origin` | 允许跨域访问的来源 | 前后端分离项目跨域问题常看它 |
| `Access-Control-Allow-Credentials` | 是否允许跨域携带 Cookie | 登录态跨域请求常关注 |
| `Access-Control-Allow-Headers` | 跨域时允许携带哪些请求头 | 自定义 token 头跨域失败时重点检查 |
| `Access-Control-Allow-Methods` | 跨域时允许哪些请求方法 | 是否允许当前接口需要的请求方法 |
| `Server` | 服务器软件信息 | 生产环境一般不建议暴露过多版本信息 |

响应头例子：

```http
HTTP/1.1 200 OK
Content-Type: application/json;charset=UTF-8
Cache-Control: no-store
Set-Cookie: sessionid=abc123; HttpOnly; Secure
Access-Control-Allow-Origin: https://www.freshmall.com
```

测试人员常见检查点：

- 返回 JSON 的接口，`Content-Type` 是否正确
- 登录接口是否返回 `Set-Cookie` 或 token
- 敏感接口是否禁止缓存，比如登录、支付、个人信息
- 跨域接口是否配置了正确的 `Access-Control-Allow-*`
- 重定向接口的 `Location` 是否跳到正确地址
- 文件下载接口的文件类型、文件名、大小是否正确



3、响应体 Body

响应体是服务器真正返回的数据。

登录成功响应例子：

```json
{
  "code": 0,
  "message": "登录成功",
  "data": {
    "userId": 1001,
    "username": "test001",
    "token": "token123"
  }
}
```

测试时要检查：

- `code` 是否符合接口文档
- `message` 提示是否正确
- `data` 数据是否完整
- 字段类型是否正确，比如 `userId` 应该是数字
- 不该返回的敏感信息是否没有返回，比如密码
- 错误场景是否返回清晰的错误信息

登录失败响应例子：

```json
{
  "code": 10001,
  "message": "用户名或密码错误",
  "data": null
}
```

测试时要确认：

- 错误码是否正确
- 错误提示是否正确
- 不应该返回 token
- 不应该登录成功



### Postman 测试举例

#### 用 Postman 测一个登录接口的例子

假设接口文档如下：

- 请求方法：`POST`
- 请求地址：`https://api.example.com/api/login`
- 请求头：`Content-Type: application/json`
- 请求体：

```json
{
  "username": "test001",
  "password": "123456"
}
```

在 Postman 中可以这样操作：

1. Method 选择 `POST`
2. URL 输入 `https://api.example.com/api/login`
3. Headers 添加 `Content-Type: application/json`
4. Body 选择 `raw`
5. Body 格式选择 `JSON`
6. 输入 JSON 请求体
7. 点击 Send
8. 查看状态码、响应体、响应时间

期望结果：

```http
HTTP/1.1 200 OK
Content-Type: application/json
```

```json
{
  "code": 0,
  "message": "登录成功",
  "data": {
    "token": "token123"
  }
}
```

可以设计的测试用例：

| 用例 | 请求数据 | 预期结果 |
| --- | --- | --- |
| 正确账号密码 | 正确 username、正确 password | 登录成功，返回 token |
| 错误密码 | 正确 username、错误 password | 登录失败，不返回 token |
| 用户名为空 | username 为空 | 提示用户名不能为空 |
| 密码为空 | password 为空 | 提示密码不能为空 |
| 少传字段 | 不传 password | 提示必填参数缺失 |
| JSON 格式错误 | 少一个右括号 | 返回请求格式错误 |
| 未设置 Content-Type | 不传 `Content-Type` | 可能解析失败或返回参数错误 |





#### 用 Postman 测一个查询用户购物车信息的例子

登录接口测完以后，通常会拿到一个 token。接下来就可以测需要登录态的接口，比如查询用户购物车信息。

这个例子的重点不是“能不能返回购物车列表”这么简单，而是看鉴权是否生效：服务器能不能根据请求头里的 token 判断当前用户是谁，并且只返回这个用户自己的购物车数据。

假设接口文档如下：

| 项目 | 内容 |
| --- | --- |
| 接口名称 | 查询用户购物车信息 |
| 请求方法 | `GET` |
| 请求地址 | `https://api.example.com/api/cart/items` |
| 是否需要登录 | 是 |
| 鉴权方式 | 请求头携带 `Authorization: Bearer token` |
| 请求参数 | 可选：`page`、`pageSize` |
| 请求体 | 无 |

在 Postman 中可以这样操作：

1. 先调用登录接口，拿到返回的 token，比如 `token123`
2. 新建一个请求，Method 选择 `GET`
3. URL 输入 `https://api.example.com/api/cart/items?page=1&pageSize=20`
4. 打开 Headers 页签
5. 添加请求头 `Authorization: Bearer token123`
6. 添加请求头 `Accept: application/json`
7. 点击 Send
8. 查看状态码、响应体、响应时间

Postman 里填写的是完整 URL：

```text
https://api.example.com/api/cart/items?page=1&pageSize=20
```

如果写成 HTTP 原始请求报文，大概是这样：

```http
GET /api/cart/items?page=1&pageSize=20 HTTP/1.1
Host: api.example.com
Accept: application/json
Authorization: Bearer token123
User-Agent: PostmanRuntime/7.39.0
```

这里最关键的是这一行：

```http
Authorization: Bearer token123
```

`Authorization` 是请求头。服务器收到请求后，会读取这个请求头中的 token，然后判断：

- token 是否存在
- token 是否正确
- token 是否过期
- token 对应的是哪个用户
- 这个用户有没有权限访问购物车接口

期望结果：

```http
HTTP/1.1 200 OK
Content-Type: application/json
```

```json
{
  "code": 0,
  "message": "查询成功",
  "data": {
    "userId": 1001,
    "total": 2,
    "items": [
      {
        "cartItemId": 501,
        "skuId": 30001,
        "goodsName": "iPhone 15 Pro 手机壳",
        "price": 39.9,
        "quantity": 1,
        "checked": true
      },
      {
        "cartItemId": 502,
        "skuId": 30002,
        "goodsName": "USB-C 数据线",
        "price": 29.9,
        "quantity": 2,
        "checked": false
      }
    ]
  }
}
```

测试时要重点看：

- 状态码是否是 `200`
- `code` 是否表示查询成功
- 响应中是否返回当前用户的购物车数据
- `total` 是否和 `items` 数量逻辑一致
- 商品名称、价格、数量、勾选状态等字段是否正确
- 不应该返回其他用户的购物车数据

可以设计的鉴权测试用例：

| 用例 | 请求头 Authorization | 预期结果 |
| --- | --- | --- |
| 正常查询 | `Bearer token123` | 返回当前用户购物车 |
| 不传 token | 不传 `Authorization` | 返回未登录或无权限 |
| token 错误 | `Bearer error_token` | 返回认证失败 |
| token 过期 | `Bearer expired_token` | 返回 token 过期，需要重新登录 |
| token 格式错误 | `token123`，少了 `Bearer` | 返回认证失败或参数格式错误 |
| A 用户 token | A 用户的 token | 只能返回 A 用户购物车 |
| B 用户 token | B 用户的 token | 只能返回 B 用户购物车 |

最后两条很重要。购物车是用户私有数据，如果用 A 用户的 token 查到了 B 用户的购物车，就是严重的越权问题。

在 Postman 里还可以把 token 保存成环境变量：

```text
{{token}}
```

然后 Headers 中写：

```http
Authorization: Bearer {{token}}
```

这样登录接口返回新 token 后，只要更新环境变量，后续购物车、订单、个人信息等接口都可以复用，不需要每个请求都手动改 token。



### 浏览器查看HTTP请求和响应：以 Edge 为例

浏览器开发者工具可以直接查看页面发出的 HTTP 请求。测试人员可以用它观察“自己在页面上点按钮时，浏览器到底请求了哪个接口、传了什么参数、返回了什么数据”。

Edge 查看步骤：

1. 打开 Microsoft Edge 浏览器
2. 打开要测试的网站
3. 按 `F12`，或者右键页面选择“检查”
4. 切换到 `网络` 或 `Network` 面板
5. 刷新页面，或者在页面上执行操作，比如登录、搜索、下单
6. 在请求列表中点击某一条请求
7. 查看右侧或下方的详细信息

Network 面板常用区域：

| 区域 | 作用 |
| --- | --- |
| `Name` | 请求名称，通常是接口路径或资源文件名 |
| `Status` | HTTP 状态码，比如 `200`、`404`、`500` |
| `Type` | 请求类型，比如 `document`、`fetch`、`xhr`、`script`、`img` |
| `Initiator` | 请求由谁发起，比如页面、JS 文件、重定向 |
| `Size` | 响应大小 |
| `Time` | 请求耗时 |

点击某个请求后，重点看这些页签：

| 页签 | 作用 |
| --- | --- |
| `Headers` | 查看请求 URL、请求方法、状态码、请求头、响应头 |
| `Payload` | 查看请求参数、表单数据、JSON 请求体 |
| `Preview` | 以更友好的结构预览响应内容 |
| `Response` | 查看原始响应体 |
| `Cookies` | 查看请求和响应中的 Cookie |
| `Timing` | 查看 DNS、连接、等待、下载等耗时明细 |

测试登录接口时可以这样看：

1. 打开登录页
2. 按 `F12` 打开开发者工具
3. 切到 `Network`
4. 勾选 `Preserve log`，避免页面跳转后请求记录被清空
5. 输入账号密码，点击登录
6. 在请求列表中筛选 `Fetch/XHR`
7. 找到类似 `/api/login` 的请求
8. 查看 `Headers` 中的请求方法、URL、状态码、请求头、响应头
9. 查看 `Payload` 中是否传了正确账号密码
10. 查看 `Response` 中是否返回 token、用户信息、业务 code、message

常用小技巧：

- `Fetch/XHR`：只看接口请求，过滤掉图片、CSS、JS 等静态资源
- `Disable cache`：禁用缓存，避免页面使用缓存导致看不到真实请求
- `Preserve log`：保留跳转前后的请求记录
- 搜索框：输入接口路径、关键字、状态码快速定位请求
- 右键请求，选择 `Copy` -> `Copy as cURL`，可以把浏览器请求复制出来给开发或导入 Postman
- 查看 `Payload`，可以确认页面实际传给后端的数据
- 查看 `Response`，可以判断是前端展示问题还是接口返回问题

例如页面提示“登录失败”，测试人员可以在 Network 中排查：

- 是否真的发出了登录请求
- 登录请求 URL 是否正确
- 请求方法是否是接口文档要求的 `POST`
- 请求体中账号密码字段名是否正确
- 请求头里是否缺少 `Content-Type`
- 响应状态码是 `200`、`400`、`401` 还是 `500`
- 响应体里的业务 `code` 和 `message` 是什么

这样就能更快判断问题在前端、后端、接口文档、测试数据还是环境配置。



### 状态码和业务码

状态码是 HTTP 协议层面的结果，比如 `200`、`404`、`500`。

业务码是系统自己定义的结果，比如：

```json
{
  "code": 10001,
  "message": "密码错误"
}
```

有些公司会这样设计：

- HTTP 状态码 `200`：请求到达服务器，并且服务器正常返回
- 业务 code `0`：业务成功
- 业务 code 非 `0`：业务失败

所以接口测试时要同时看：

- HTTP 状态码
- 响应体中的业务 code
- 响应体中的 message
- 响应体中的 data

```kotlin
val response = client.newCall(request).execute()
```

## 接口文档

接口文档就是对接口的说明书。它告诉我们：这个接口是做什么的、怎么请求、需要传哪些参数、会返回什么结果、有哪些错误情况。

站在测试人员角度，接口文档非常重要。因为我们做接口测试时，不能只靠猜接口怎么用，而是要根据接口文档去设计测试用例、准备测试数据、发送请求、检查响应结果。

### 接口文档是谁提供的？

通常由后端开发提供。

因为接口一般是后端开发设计和实现的，所以后端最清楚：

- 接口地址是什么
- 请求方法是什么
- 需要哪些参数
- 参数类型是什么
- 哪些参数必填
- 返回数据结构是什么
- 错误码有哪些
- 是否需要登录或权限

但在实际项目中，接口文档可能由不同角色一起维护：

| 角色 | 可能负责的内容 |
| --- | --- |
| 后端开发 | 编写接口地址、参数、返回值、错误码 |
| 前端开发 | 根据接口文档调用接口，也可能补充前端需要的字段 |
| 测试人员 | 根据文档设计测试用例，并发现文档不清楚或不一致的问题 |
| 产品经理 | 说明业务规则，比如登录失败提示、订单状态含义 |
| 项目负责人 | 推动接口文档及时更新 |

测试人员要注意：接口文档不一定永远正确。接口测试时如果发现实际返回和文档不一致，要及时和开发确认，是接口有 bug，还是文档没有更新。

### 接口文档是什么？

接口文档可以理解为接口测试的“需求说明书”。

一份比较完整的接口文档，通常包含：

- 接口名称：这个接口是做什么的
- 接口地址：请求 URL
- 请求方法：GET、POST、PUT、DELETE 等
- 请求头：比如 `Content-Type`、`Authorization`
- 请求参数：传哪些字段，字段类型是什么
- 参数说明：字段含义、是否必填、长度限制、取值范围
- 请求示例：给一个可以参考的请求数据
- 响应示例：接口成功时返回什么
- 错误示例：接口失败时返回什么
- 状态码或业务码：比如 `code=0` 表示成功
- 鉴权要求：是否需要登录、token、权限
- 业务规则：比如密码错误 5 次后锁定账号

测试人员看接口文档时，不能只看“怎么调通接口”，还要看“怎么测出问题”。

### 接口文档的常见方式

实际工作中，接口文档可能有很多形式。

| 方式 | 说明 |
| --- | --- |
| Word / Excel 文档 | 比较传统，适合简单项目，但更新不方便 |
| Markdown 文档 | 程序员常用，方便写接口说明 |
| Swagger / Knife4j | 常见的在线接口文档，可以直接查看接口、参数、响应 |
| Postman Collection | 可以把接口集合导入 Postman，直接调试 |
| Apifox / Apipost | 专门的接口管理平台，支持文档、调试、Mock、测试 |
| 后端代码注解生成 | 根据后端代码自动生成接口文档 |
| 项目 Wiki / 禅道 / Confluence | 团队统一维护接口说明 |

常见情况：

- 中小项目可能直接用 Apifox、Apipost
- Java 项目中 Swagger、Knife4j 很常见
- 测试人员使用 Postman 时，经常会导入接口集合或根据文档手动创建请求

#### 登录凭证 token 怎么理解？

很多初学者会误以为有两个登录接口：一个普通登录接口，一个带 token 的登录接口。

更准确的理解是：

1. 第一次登录时，用户还没有 token

   所以登录接口一般只需要传账号和密码。服务器验证账号密码正确后，会返回一个 token。

2. 登录成功后，token 就相当于“登录凭证”

   后续再访问购物车、订单、个人信息这些需要登录的接口时，就不用每次都传账号密码了，而是带上 token。

3. 服务器通过 token 判断当前用户是谁

   如果 token 正确，说明用户已经登录；如果 token 缺失、错误或过期，说明用户未登录或登录失效。

可以简单理解：

- 账号密码：用来换取 token
- token：用来证明“我已经登录过”

常见流程：

```text
1. 调用登录接口，传 username 和 password
2. 登录成功，服务器返回 token
3. Postman 保存这个 token
4. 请求购物车、订单、个人信息等接口时，在 Header 里带上 token
5. 服务器识别 token，返回当前用户的数据
```

例如登录成功后返回：

```json
{
  "code": 0,
  "message": "登录成功",
  "data": {
    "token": "token123"
  }
}
```

后续请求需要登录的接口时，Header 里这样传：

```http
Authorization: Bearer token123
```

注意：`Bearer token123` 是一种常见写法，意思是“我携带的登录凭证是 token123”。不同项目写法可能不一样，有些项目可能直接写 token，有些项目可能用 Cookie，有些项目可能请求头名字叫 `X-Token`。



#### 常见登录凭证形式：token、jwt_token、Cookie、Session

不同项目保存登录状态的方式不完全一样，但目的都是一样的：让服务器知道“当前请求是谁发的”。

初学者可以先这样理解：

| 名称 | 简单理解 | 常见传递位置 |
| --- | --- | --- |
| token | 一串登录凭证 | Header、Params、Body |
| jwt_token | 一种特殊格式的 token | Header 最常见 |
| Cookie | 浏览器自动保存和携带的一小段数据 | Cookie |
| Session | 服务器保存的登录会话 | 通常配合 Cookie 使用 |

##### 1. 普通 token

普通 token 就是一串登录凭证，可能长这样：

```text
43a2d8e33a7b439c83faabcd4919abdd
```

登录成功后，服务器返回 token：

```json
{
  "code": 0,
  "message": "登录成功",
  "data": {
    "token": "43a2d8e33a7b439c83faabcd4919abdd"
  }
}
```

后续请求时，可能这样传：

```http
Authorization: 43a2d8e33a7b439c83faabcd4919abdd
```

也可能这样传：

```http
X-Token: 43a2d8e33a7b439c83faabcd4919abdd
```

测试人员要看接口文档要求，不同项目请求头名字可能不一样。

##### 2. jwt_token

JWT 全称是 JSON Web Token。它也是 token 的一种，只是格式更特殊。

JWT 通常长得比较长，中间有两个点，分成三段：

```text
xxxxx.yyyyy.zzzzz
```

真实项目里可能类似这样：

```text
eyJhbGciOiJIUzI1NiJ9.eyJ1c2VySWQiOjEwMDF9.abc123signature
```

初学者不用一开始就研究 JWT 的加密细节，只要先记住：

- jwt_token 是一种 token
- 它通常由三段组成，中间用 `.` 分隔
- 它里面可能包含用户 ID、过期时间等信息
- 它一般放在 Header 里传给服务器

常见写法：

```http
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.eyJ1c2VySWQiOjEwMDF9.abc123signature
```

有些接口文档会把字段名写成：

```json
{
  "jwt_token": "eyJhbGciOiJIUzI1NiJ9.eyJ1c2VySWQiOjEwMDF9.abc123signature"
}
```

这时后续请求依然可能是放到 Header 里：

```http
Authorization: Bearer {{jwt_token}}
```

在 Postman 中，常见做法是把登录接口返回的 `jwt_token` 保存成环境变量，然后其他接口直接引用。

##### 3. Cookie

Cookie 是浏览器常用的一种保存登录状态的方式。

它的流程通常是：

```text
1. 用户登录成功
2. 服务器在响应头里返回 Set-Cookie
3. 浏览器保存 Cookie
4. 后续请求同一个网站时，浏览器自动带上 Cookie
5. 服务器根据 Cookie 判断用户是否登录
```

登录成功响应头可能长这样：

```http
Set-Cookie: sessionId=abc123; Path=/; HttpOnly
```

后续请求时，客户端会带上：

```http
Cookie: sessionId=abc123
```

在 Postman 里，也可以手动添加 Cookie，或者使用 Postman 自带的 Cookies 管理功能。

测试人员要注意：

- Cookie 是否登录成功后正确返回
- 后续请求是否自动带上 Cookie
- 删除 Cookie 后是否变成未登录
- Cookie 过期后是否需要重新登录
- 退出登录后 Cookie 是否失效

##### 4. Session

Session 通常和 Cookie 一起出现。

可以这样理解：

- Cookie 保存在客户端，比如浏览器或 Postman
- Session 保存在服务器
- Cookie 里通常保存一个 sessionId
- 服务器根据 sessionId 找到对应的 Session，判断用户是谁

举个简单例子：

```text
客户端 Cookie：sessionId=abc123
服务器 Session：abc123 对应用户 test001
```

当客户端请求购物车接口时：

```http
GET /api/cart/items HTTP/1.1
Host: example.com
Cookie: sessionId=abc123
```

服务器看到 `sessionId=abc123`，就知道当前用户是 `test001`，然后返回这个用户的购物车。

##### Cookie 和 Session 的区别

Cookie 和 Session 经常一起出现，但它们不是同一个东西。

简单理解：

- Cookie 是客户端保存的一小段数据
- Session 是服务器保存的一份会话数据
- Cookie 里经常只保存一个 `sessionId`
- 服务器拿到 `sessionId` 后，再去服务器内存、Redis 或数据库里查对应的 Session

对比一下：

| 对比点 | Cookie | Session |
| --- | --- | --- |
| 保存位置 | 客户端，比如浏览器、Postman | 服务器端，比如内存、Redis、数据库 |
| 谁创建 | 通常由服务器通过 `Set-Cookie` 下发，也可以由前端写入 | 服务器创建 |
| 谁携带 | 客户端后续请求自动或手动携带 | 不会直接发送给客户端 |
| 常见内容 | `sessionId=abc123`、设备标识、偏好设置等 | 用户 ID、登录状态、权限、过期时间等 |
| 安全性 | 客户端可见，可能被清理、篡改或窃取 | 服务端保存，相对更安全 |
| 过期控制 | Cookie 自己有过期时间 | Session 也有服务端过期时间 |
| 测试关注 | 是否正确 Set-Cookie、是否自动携带、退出后是否清除 | sessionId 是否能匹配正确用户、过期是否生效、是否存在越权 |

完整流程可以这样看：

```text
1. 用户登录成功
2. 服务器创建 Session，例如 sess_abc123 -> 用户 test001
3. 服务器在响应头返回 Set-Cookie: sessionId=sess_abc123
4. 浏览器保存 Cookie
5. 后续请求自动携带 Cookie: sessionId=sess_abc123
6. 服务器根据 sessionId 找到 Session
7. 服务器确认当前用户是 test001，再返回对应数据
```

所以，接口测试时不要只看有没有 `Cookie`，还要看它背后的 Session 是否真的生效。

比如测试购物车接口时：

- 不带 Cookie，应该返回未登录
- 带错误 `sessionId`，应该返回登录失效或认证失败
- 带过期 `sessionId`，应该要求重新登录
- A 用户的 `sessionId` 只能查到 A 用户购物车
- 退出登录后，原来的 `sessionId` 应该失效

还有一种项目写法是把会话 ID 放在请求头里，而不是 Cookie 里：

```http
Session: sess_abc123
```

或者：

```http
X-Session-Id: sess_abc123
```

这种属于项目自定义规则，不是所有系统都这么写。测试时以接口文档为准，看清楚会话 ID 到底要求放在 `Cookie`、`Session` 请求头，还是 `X-Session-Id` 请求头里。

##### 5. token 和 Cookie 的区别

| 对比点 | token / jwt_token | Cookie / Session |
| --- | --- | --- |
| 常见位置 | Header 中较常见 | Cookie 中 |
| 常见场景 | App、前后端分离项目、小程序 | 传统 Web 网站 |
| 是否自动携带 | 通常需要前端或工具主动带上 | 浏览器通常会自动携带 |
| Postman 使用 | 常在 Headers 或 Authorization 中配置 | 可以在 Cookies 中管理 |
| 测试重点 | token 缺失、错误、过期、篡改 | Cookie 缺失、过期、退出后失效 |

不用死记哪个更高级，测试时最重要的是看接口文档：

- 登录成功后返回的是 token、jwt_token，还是 Set-Cookie？
- 后续接口要求把凭证放在哪里？
- Header 名字是什么？
- 是否需要加 `Bearer`？
- 凭证多久过期？
- 退出登录后凭证是否失效？

##### 6. Postman 里怎么处理这些登录凭证？

如果是 token 或 jwt_token：

1. 先调用登录接口
2. 从响应体里复制 token
3. 打开需要登录的接口
4. 在 Headers 里添加：

```http
Authorization: Bearer token值
```

或者：

```http
X-Token: token值
```

如果是 Cookie：

1. 先调用登录接口
2. 查看响应头是否有 `Set-Cookie`
3. Postman 通常会保存 Cookie
4. 再请求需要登录的接口
5. 检查请求里是否带上了 Cookie

##### 7. 测试人员常见测试点

无论项目用 token、jwt_token，还是 Cookie，测试思路都类似。

| 测试点 | 用例示例 | 预期结果 |
| --- | --- | --- |
| 正确凭证 | 带正确 token 或 Cookie 请求 | 请求成功 |
| 不带凭证 | 不传 token / Cookie | 返回未登录 |
| 错误凭证 | 随便写一个 token / Cookie | 返回认证失败 |
| 过期凭证 | 使用过期 token / Cookie | 返回登录过期 |
| 篡改凭证 | 修改 token 中的几个字符 | 返回认证失败 |
| 退出登录 | 退出后继续用原凭证请求 | 应该失效 |
| 用户隔离 | 用 A 用户凭证请求 | 只能看到 A 用户自己的数据 |
| 权限控制 | 普通用户访问管理员接口 | 返回无权限 |

一句话记住：

登录凭证不管叫什么，token、jwt_token、Cookie，本质上都是为了证明“我是谁、我是否登录、我有没有权限”。

#### 补充接口：获取当前登录用户信息

有些项目会提供一个“获取当前登录用户信息”的接口，用来校验 token 是否有效，也可以用来获取当前登录用户资料。

这个接口不是登录接口，而是“带 token 查询当前登录用户”的接口。

| 项目 | 内容 |
| --- | --- |
| 接口名称 | 获取当前登录用户信息 |
| 接口说明 | 根据 token 查询当前登录用户的信息 |
| 请求方法 | GET |
| 请求地址 | `/api/user/profile` |
| 是否需要登录 | 是 |
| 请求数据格式 | 无请求体 |
| 响应数据格式 | JSON |

请求头 Headers：

| 参数名 | 是否必填 | 示例 | 说明 |
| --- | --- | --- | --- |
| `Authorization` | 是 | `Bearer token123` | 登录凭证 |

请求示例：

```http
GET /api/user/profile HTTP/1.1
Host: example.com
Authorization: Bearer token123
```

成功响应示例：

```json
{
  "code": 0,
  "message": "查询成功",
  "data": {
    "userId": 1001,
    "username": "test001",
    "nickname": "测试用户",
    "mobile": "13800138000"
  }
}
```

未传 token 或 token 无效：

```json
{
  "code": 401,
  "message": "请先登录",
  "data": null
}
```

测试人员可以这样区分：

| 接口 | 是否传账号密码 | 是否传 token | 作用 |
| --- | --- | --- | --- |
| 登录接口 `/api/login` | 是 | 否 | 用账号密码登录，获取 token |
| 当前用户信息 `/api/user/profile` | 否 | 是 | 用 token 查询当前登录用户 |
| 购物车列表 `/api/cart/items` | 否 | 是 | 用 token 查询当前用户购物车 |

所以，不是所有带 token 的接口都叫登录接口。登录接口负责“发 token”，其他需要登录的接口负责“验证 token 并返回用户相关数据”。

### 接口文档举例：购物车商品列表接口

购物车商品列表接口和登录接口不一样，它通常需要用户先登录。

因为购物车数据是属于某个用户的，服务器必须知道“当前是谁在查询购物车”。所以请求这个接口时，一般要在请求头里携带登录后获得的 token。

#### 基本信息

| 项目 | 内容 |
| --- | --- |
| 接口名称 | 查询购物车商品列表 |
| 接口说明 | 查询当前登录用户购物车中的商品 |
| 请求方法 | GET |
| 请求地址 | `/api/cart/items` |
| 是否需要登录 | 是 |
| 请求数据格式 | 无请求体 |
| 响应数据格式 | JSON |

#### 请求头 Headers

| 参数名 | 是否必填 | 示例 | 说明 |
| --- | --- | --- | --- |
| `Authorization` | 是 | `Bearer token123` | 登录凭证，用来识别当前用户 |
| `Content-Type` | 否 | `application/json` | GET 请求通常没有 Body，可以不传 |

重点注意：

- `Authorization` 是这个接口的关键
- 没有 token，服务器不知道是谁在查购物车
- token 错误、过期、被篡改时，接口应该返回未登录或认证失败

#### 请求参数 Params

购物车列表接口有时不需要参数，直接查询当前登录用户的购物车。

如果支持分页，可能会有这些参数：

| 参数名 | 类型 | 是否必填 | 示例 | 说明 |
| --- | --- | --- | --- | --- |
| `page` | number | 否 | `1` | 当前页码，默认第 1 页 |
| `size` | number | 否 | `10` | 每页数量，默认 10 条 |

请求示例：

```http
GET /api/cart/items?page=1&size=10 HTTP/1.1
Host: example.com
Authorization: Bearer token123
```

在 Postman 中可以这样填写：

- Method 选择 `GET`
- URL 填写 `https://example.com/api/cart/items`
- Params 中填写 `page=1`、`size=10`
- Headers 中填写 `Authorization: Bearer token123`
- Body 选择 `none`

#### 测试人员重点关注什么？

这个接口是需要登录信息的，所以测试重点不只是“能不能返回购物车列表”，还要重点测鉴权。

可以设计这些测试用例：

| 测试点 | 用例示例 | 预期结果 |
| --- | --- | --- |
| 正常查询 | 携带正确 token 查询 | 返回当前用户的购物车列表 |
| 未登录 | 不传 `Authorization` | 返回请先登录 |
| token 错误 | 传一个随便写的 token | 返回认证失败 |
| token 过期 | 使用过期 token | 返回登录已过期 |
| token 被篡改 | 修改 token 中的部分字符 | 返回认证失败 |
| 用户隔离 | A 用户 token 查询 | 只能看到 A 用户自己的购物车 |
| 空购物车 | 已登录但购物车为空 | 返回空列表，而不是报错 |
| 分页正常 | `page=1&size=10` | 返回对应分页数据 |
| 分页异常 | `page=0` 或 `size=-1` | 返回分页参数错误 |
| 字段检查 | 检查商品名称、价格、数量、库存 | 字段完整，类型正确 |
| 敏感信息 | 查看响应是否返回用户密码等信息 | 不应该返回敏感信息 |

测试人员要特别注意“用户隔离”：

如果用 A 用户的 token 查询到了 B 用户的购物车，这就是很严重的问题。接口测试不能只看接口有没有返回数据，还要看返回的数据是不是属于当前登录用户。

### 测试人员拿到接口文档后要看什么？

测试人员拿到接口文档后，不要急着直接发请求，可以先检查这些内容：

1. 接口基本信息是否清楚

   比如接口名称、接口地址、请求方法、接口用途是否写明白。

2. 请求参数是否完整

   要看每个参数的字段名、类型、是否必填、默认值、长度限制、取值范围。

3. 请求头是否说明清楚

   比如是否需要 `Content-Type`，是否需要 `Authorization`，token 放在哪里。

4. 返回结果是否完整

   要看成功返回什么，失败返回什么，字段类型是什么，是否有响应示例。

5. 错误码是否明确

   比如参数错误、未登录、无权限、数据不存在分别返回什么。

6. 业务规则是否写清楚

   比如登录失败几次锁定账号、订单什么状态可以取消、优惠券是否过期。

7. 文档和实际接口是否一致

   如果文档写的是 POST，但实际只能 GET；或者文档写返回 `userName`，实际返回 `username`，都需要记录并反馈。

### 根据接口文档设计测试用例

以登录接口为例，可以从文档中提取测试点。

| 测试点 | 用例示例 | 预期结果 |
| --- | --- | --- |
| 正常场景 | 正确账号、正确密码 | 登录成功，返回 token |
| 必填校验 | 不传 username | 提示用户名不能为空 |
| 必填校验 | 不传 password | 提示密码不能为空 |
| 参数类型 | username 传数字 | 根据需求返回参数错误或正常转字符串 |
| 参数长度 | password 超过最大长度 | 返回参数错误 |
| 业务规则 | 密码错误 | 登录失败，不返回 token |
| 业务规则 | 冻结账号登录 | 提示账号被冻结 |
| 安全检查 | 响应中是否返回密码 | 不应该返回密码 |
| 请求头检查 | 不传 `Content-Type` | 可能返回参数格式错误 |
| 请求方法检查 | 用 GET 请求登录接口 | 返回方法不允许或接口不存在 |

所以接口文档不是只用来“照着发请求”的，它还能帮助我们设计正向用例、反向用例、边界用例、异常用例。

### 接口文档不清楚时怎么办？

实际工作里，经常会遇到接口文档写得不完整。

比如：

- 没写参数是否必填
- 没写字段类型
- 没写错误码
- 没写失败响应示例
- 没写是否需要登录
- 文档和实际返回不一致

测试人员可以这样处理：

- 先根据现有文档尝试调用接口
- 把不清楚的地方整理成问题
- 找后端开发或产品确认
- 确认后补充到测试用例或接口文档中
- 如果实际结果和文档不一致，要提交 bug 或让开发更新文档

常见沟通问题可以这样问：

- 这个参数是必填还是选填？
- 这个字段最大长度是多少？
- 这个接口是否需要 token？
- token 是放在 Header 里还是 Cookie 里？
- 密码错误时应该返回什么错误码？
- 用户不存在和密码错误是否要区分提示？
- 这个字段为空时应该返回 null、空字符串，还是不返回？









# 接口自动化测试

## 接口自动化测试用例设计思路与要点

接口自动化测试不是把手工接口用例简单复制到代码里，而是要选择适合长期回归、结果稳定、断言明确的接口场景进行自动化。

设计接口自动化用例时，可以按照下面的思路来分析：

1. 先明确测试目标

   接口自动化主要用于回归测试、冒烟测试、主流程验证、核心接口监控。

   例如登录、下单、支付回调、查询订单、修改用户信息等核心接口，适合优先自动化。

2. 根据接口文档拆分测试点

   从接口文档中提取请求地址、请求方式、请求头、请求参数、响应字段、错误码、业务规则等信息。

   每一个测试点都要能形成明确的输入和预期输出。

3. 优先覆盖核心业务流程

   自动化用例不是越多越好，要先覆盖稳定且重要的链路。

   比如电商系统可以先覆盖：

   - 登录
   - 查询商品
   - 加入购物车
   - 提交订单
   - 查询订单

4. 区分正向用例和反向用例

   正向用例主要验证接口在正常参数下是否能成功返回。

   反向用例主要验证接口在异常参数、缺少参数、权限不足、数据不存在等情况下是否能正确处理。

5. 明确断言内容

   接口自动化的重点不是“请求能发出去”，而是“结果是否符合预期”。

   常见断言包括：

   - 状态码断言：如 `200`、`401`、`403`、`404`、`500`
   - 业务码断言：如 `code = 0`、`code = 10001`
   - 响应字段断言：如返回中必须包含 `token`、`userId`
   - 字段类型断言：如 `id` 是数字，`name` 是字符串
   - 字段值断言：如用户名、订单状态、商品数量是否正确
   - 数据库断言：如下单成功后数据库是否新增订单记录
   - 业务规则断言：如未登录不能访问个人信息接口

6. 处理接口依赖关系

   很多接口不是独立存在的，后一个接口可能依赖前一个接口的返回值。

   例如：

   - 登录接口返回 `token`
   - 查询用户信息接口需要带上 `token`
   - 创建订单接口需要商品 `id`
   - 支付接口需要订单 `orderId`

   所以自动化脚本中要能提取上一个接口的响应数据，并传给后续接口使用。

7. 设计测试数据

   自动化用例要尽量保证数据可重复执行。

   常见做法：

   - 使用固定测试账号
   - 执行前准备测试数据
   - 执行后清理测试数据
   - 使用随机数、时间戳避免数据重复
   - 将测试数据放到 Excel、YAML、JSON 或数据库中统一维护

8. 注意环境和配置

   接口自动化通常会在不同环境执行，比如测试环境、预发布环境、生产监控环境。

   所以请求地址、账号、密码、数据库连接、请求头等配置不要写死在脚本里，应该统一放到配置文件中。

9. 关注用例稳定性

   自动化用例最怕不稳定。

   容易导致用例不稳定的原因有：

   - 测试数据被别人修改
   - 接口依赖第三方服务
   - 环境不稳定
   - 断言写得太模糊
   - 用例之间强依赖但执行顺序混乱
   - 执行后没有清理脏数据

10. 设计用例优先级

    可以按照接口重要程度和风险来划分优先级。

    - P0：核心主流程，冒烟测试必须执行
    - P1：重要功能和常见异常场景
    - P2：边界值、兼容性、低频异常场景
    - P3：补充场景或低风险场景

### 接口自动化用例常见字段

接口自动化用例一般可以包含下面这些字段：

| 字段 | 说明 |
| --- | --- |
| 用例编号 | 用来唯一标识一条用例，如 `API_LOGIN_001` |
| 用例标题 | 简要说明这条用例验证什么 |
| 接口模块 | 如登录、用户、商品、订单、支付 |
| 接口地址 | 请求的 URL 或路径 |
| 请求方式 | 如 GET、POST、PUT、DELETE |
| 是否需要登录 | 是否需要 token、Cookie 或其他鉴权信息 |
| 请求头 | 如 `Content-Type`、`Authorization` |
| 前置条件 | 执行该用例前需要满足的条件 |
| 请求参数 | Query、Path、Body 中的参数 |
| 依赖数据 | 是否依赖其他接口返回值 |
| 预期状态码 | HTTP 状态码预期结果 |
| 预期业务码 | 响应体中的业务 code |
| 断言内容 | 要检查哪些响应字段或业务结果 |
| 数据库校验 | 是否需要检查数据库数据 |
| 优先级 | P0、P1、P2、P3 |
| 是否自动化 | 是否纳入自动化执行 |
| 备注 | 特殊说明 |

### 接口自动化用例设计示例

以登录接口为例：

| 编号 | 标题 | 接口类别 | 请求地址 | 请求方式 | 是否需要登录 | 请求参数 | 预期结果 | 断言点 | 优先级 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| API_LOGIN_001 | 正确账号密码登录成功 | 登录 | `/api/login` | POST | 否 | `username=zhangsan`，`password=123456` | 登录成功，返回 token | 状态码为 200；`code=0`；返回 `token` | P0 |
| API_LOGIN_002 | 用户名为空登录失败 | 登录 | `/api/login` | POST | 否 | `username=`，`password=123456` | 提示用户名不能为空 | 状态码为 200 或 400；业务码符合文档；错误信息正确 | P1 |
| API_LOGIN_003 | 密码为空登录失败 | 登录 | `/api/login` | POST | 否 | `username=zhangsan`，`password=` | 提示密码不能为空 | 业务码符合文档；不返回 `token` | P1 |

### 设计接口自动化用例时的注意事项

1. 不建议一开始就把所有接口都自动化

   应该先从稳定、核心、重复执行频率高的接口开始。

2. 不要只断言状态码

   有些接口即使业务失败，HTTP 状态码也可能是 `200`，所以还要断言业务码、响应字段和业务数据。

3. 用例之间尽量降低依赖

   如果依赖太多，前面一条失败可能导致后面一批用例都失败。

4. 测试数据要可控

   自动化执行前要知道使用什么数据，执行后要知道是否需要清理数据。

5. 失败结果要容易定位

   自动化报告中应该能看到请求地址、请求参数、响应结果、断言失败原因。

6. 和接口文档保持一致

   如果自动化结果和接口文档不一致，要判断是接口 bug、文档问题，还是自动化脚本问题。

7. 接口自动化要持续维护

   接口字段、业务规则、错误码变化后，用例和断言也要同步更新。

总结：接口自动化测试用例设计的核心是“选对接口、准备数据、明确断言、处理依赖、保证稳定”。自动化不是为了追求数量，而是为了让核心接口在每次迭代后都能快速、稳定地完成回归验证。





## Excel接口测试用例访问

接口自动化中，Excel 常用来维护接口测试用例和测试数据。它的优点是直观、容易编辑、适合初学和中小型项目。

常见思路是：把每一行当成一条测试用例，把每一列当成用例字段，Python 读取 Excel 后循环执行接口请求。

### Excel 用例字段示例

| case_id | title | method | url | headers | params | body | expected_status | expected_code | check_field | priority | run |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| API_LOGIN_001 | 正确账号密码登录成功 | POST | `/api/login` | `{"Content-Type":"application/json"}` |  | `{"username":"zhangsan","password":"123456"}` | 200 | 0 | token | P0 | yes |
| API_LOGIN_002 | 密码错误登录失败 | POST | `/api/login` | `{"Content-Type":"application/json"}` |  | `{"username":"zhangsan","password":"error123"}` | 200 | 10001 | message | P1 | yes |

字段说明：

- `case_id`：用例编号，建议唯一
- `title`：用例标题
- `method`：请求方式，如 GET、POST、PUT、DELETE
- `url`：接口地址，可以是完整地址，也可以是接口路径
- `headers`：请求头，通常用 JSON 字符串保存
- `params`：GET 请求参数，通常用 JSON 字符串保存
- `body`：POST 请求体，通常用 JSON 字符串保存
- `expected_status`：预期 HTTP 状态码
- `expected_code`：预期业务 code
- `check_field`：需要检查的响应字段
- `priority`：用例优先级
- `run`：是否执行，`yes` 表示执行，`no` 表示跳过

### Python 使用 Pandas 读取 Excel

```python
import json
import pandas as pd


def parse_json_cell(value):
    """把 Excel 单元格中的 JSON 字符串转成 Python 字典。"""
    if pd.isna(value) or value == "":
        return {}
    return json.loads(value)


cases = pd.read_excel("api_cases.xlsx", sheet_name="login")

for _, case in cases.iterrows():
    if str(case["run"]).lower() != "yes":
        continue

    case_id = case["case_id"]
    title = case["title"]
    method = case["method"].upper()
    url = "http://test.example.com" + case["url"]
    headers = parse_json_cell(case["headers"])
    params = parse_json_cell(case["params"])
    body = parse_json_cell(case["body"])

    print(case_id, title, method, url)
```



使用 Excel 管理接口测试用例时要注意：

- 字段名尽量使用英文，方便 Python 读取和维护
- JSON 字符串要写成标准格式，双引号不能省略
- 不同模块可以放在不同 Sheet 中，如 `login`、`order`、`product`
- 敏感信息不要直接写在 Excel 中，可以放到配置文件或环境变量中
- Excel 适合用例数量不太大、协作人员不太多的项目











## MySQL数据库接口测试用例访问

当接口用例数量越来越多，或者需要多人协作、统一管理、按条件查询时，可以把接口测试用例放到 MySQL 数据库中。

相比 Excel，MySQL 管理接口测试用例有这些特点：

| 对比项 | Excel | MySQL |
| --- | --- | --- |
| 使用难度 | 简单，适合初学 | 需要建表和 SQL 基础 |
| 数据量 | 适合少量用例 | 适合大量用例 |
| 多人协作 | 容易冲突 | 更适合多人维护 |
| 查询能力 | 筛选能力有限 | 可以按模块、优先级、是否执行等条件查询 |
| 数据规范 | 容易手误 | 可以通过字段类型、约束控制 |
| 版本管理 | 不方便 | 可以配合平台或脚本管理 |
| 维护成本 | 前期低，后期高 | 前期高，后期更稳定 |

所以 Excel 更适合学习、演示、小项目；MySQL 更适合公司内部平台化、用例数量较多、需要长期维护的接口自动化项目。

### 用例管理思路

实际项目中可以这样管理接口自动化用例：

1. 初期用 Excel 设计和评审测试用例

   Excel 更直观，方便测试、开发、产品一起确认字段和场景。

2. 用例稳定后导入 MySQL

   把 Excel 中的字段映射到数据库字段，比如 `case_id`、`title`、`method`、`url`、`body`、`expected_code`。

3. 自动化脚本统一从 MySQL 读取用例

   脚本不关心用例写在哪里，只负责读取数据、发送请求、执行断言、生成报告。

4. 后续可以做成接口测试平台

   在页面上新增、编辑、禁用、执行测试用例，底层仍然可以用 MySQL 保存数据。

总结：Excel 适合“写用例和学习”，MySQL 适合“统一管理和长期维护”。接口自动化框架真正要做到的是数据和代码分离，让测试数据可以独立维护，让执行逻辑保持稳定。











## ⭐PyTest自动化测试框架

PyTest 是 Python 中常用的自动化测试框架，适合做单元测试、自动化测试脚本管理等。

- 插件丰富，可以生成测试报告、控制用例执行顺序、失败重跑等

在自动化测试中，PyTest 常用来组织测试用例、执行断言、管理测试数据、生成测试报告。

### PyTest 使用约束

PyTest 对文件名、类名、函数名有一定命名规则，符合规则的用例才会被自动收集。

常见约束：

- 测试文件名一般以 `test_` 开头，或以 `_test.py` 结尾
- 测试函数名必须以 `test_` 开头
- 测试类名必须以 `Test` 开头，测试类中不要写 `__init__` 方法
- 测试类中的测试方法必须以 `test_` 开头
- 普通工具函数不要以 `test_` 开头，否则可能被当成测试用例执行

示例：

```python
class TestLogin:
    def test_login_success(self):
        assert True

    def test_login_fail(self):
        assert 1 == 1
```

下面这种写法不会被 PyTest 当成测试用例：

```python
def login_success():
    assert True


class LoginTest:
    def login_fail(self):
        assert True
```

原因是函数名没有以 `test_` 开头，类名也没有以 `Test` 开头。



### PyTest 断言

PyTest 直接使用 Python 的 `assert` 进行断言。

常见断言写法：

```python
def test_assert_demo():
    status_code = 200
    result = {
        "code": 0,
        "message": "success",
        "data": {
            "token": "abc123",
            "user_id": 1001
        }
    }

    assert status_code == 200
    assert result["code"] == 0
    assert result["message"] == "success"
    assert "token" in result["data"]
    assert result["data"]["user_id"] == 1001
```



带错误提示的断言：

```python
def test_login_code():
    result = {"code": 10001, "message": "密码错误"}

    assert result["code"] == 0, "登录接口业务码不符合预期"
```

断言失败后，PyTest 会显示失败位置、实际结果和预期结果，方便定位问题。



### PyTest 参数化

参数化可以用一段测试代码执行多组测试数据，适合接口自动化中的正向、反向、边界值场景。

使用 `@pytest.mark.parametrize` 实现参数化。

简单示例：

```python
import pytest


@pytest.mark.parametrize(
    "username,password,expected_code",
    [
        ("zhangsan", "123456", 0),
        ("zhangsan", "error123", 10001),
        ("", "123456", 10002),
        ("zhangsan", "", 10003),
    ]
)
def test_login(username, password, expected_code):
    result = login(username, password)

    assert result["code"] == expected_code


def login(username, password):
    if username == "":
        return {"code": 10002, "message": "用户名不能为空"}
    if password == "":
        return {"code": 10003, "message": "密码不能为空"}
    if password != "123456":
        return {"code": 10001, "message": "密码错误"}
    return {"code": 0, "message": "登录成功"}
```

### ⭐Fixture

Fixture 是 PyTest 中非常重要的前置、后置和数据准备机制。

可以把 Fixture 理解成“测试用例运行前后需要用到的公共准备函数”。

它常用于：

- 准备测试数据
- 初始化对象
- 登录并获取 token
- 创建数据库连接
- 打开浏览器
- 执行接口请求前的公共准备
- 测试结束后清理数据、关闭连接、退出浏览器
- ......



#### Fixture 是什么？

Fixture 本质上是一个被 `@pytest.fixture` 装饰的函数。

普通函数不会被 PyTest 当成 Fixture，只有加了 `@pytest.fixture`，PyTest 才知道这个函数可以作为测试用例的依赖。

测试用例想使用某个 Fixture 时，只需要把 Fixture 的函数名写到测试函数的参数中，PyTest 会在执行测试用例前自动执行这个 Fixture，并把 Fixture 的返回值传给测试用例。

基本格式：

```python
import pytest


@pytest.fixture
def login_token():
    return "token_abc123"


def test_get_user_info(login_token):
    print(login_token)
    assert login_token == "token_abc123"
```

执行逻辑：

```text
1. PyTest 发现 test_get_user_info 需要 login_token
2. PyTest 先执行 login_token 这个 Fixture
3. login_token 返回 "token_abc123"
4. PyTest 把返回值传给 test_get_user_info 的 login_token 参数
5. 执行测试用例
```

注意：Fixture 的调用方式不是 `login_token()`，而是把 `login_token` 写到测试函数参数里。

错误写法：

```python
def test_get_user_info():
    token = login_token()
    assert token
```



#### Fixture 的优点

1. 可以复用公共前置代码

   多个测试用例都需要登录时，不用每个用例都写一遍登录逻辑，可以把登录逻辑放到 Fixture 中。

2. 测试用例更简洁

   测试用例只关注“测什么”和“断言什么”，准备数据、登录、清理数据等公共逻辑交给 Fixture。

3. 支持前置和后置

   Fixture 不只能做前置操作，也可以使用 `yield` 实现后置清理。

4. 支持作用域控制

   可以控制 Fixture 是每个用例执行一次，还是每个类、每个模块、整个测试会话只执行一次。

5. 可以互相依赖

   一个 Fixture 可以直接使用另一个 Fixture，适合把复杂准备过程拆成多个小步骤。

6. 可以自动执行

   使用 `autouse=True` 后，测试用例不需要显式传参，Fixture 也会自动执行。

7. 可以放到 `conftest.py` 统一管理

   多个测试文件都要使用的 Fixture，可以统一放到 `conftest.py` 中，不需要每个测试文件重复定义。



#### Fixture 基本用法

最基础的用法是：定义 Fixture，然后测试用例通过参数名使用它。

```python
import pytest


@pytest.fixture
def user_info():
    user = {
        "id": 1001,
        "username": "zhangsan",
        "role": "buyer"
    }
    return user


def test_user_name(user_info):
    assert user_info["username"] == "zhangsan"


def test_user_role(user_info):
    assert user_info["role"] == "buyer"
```

这里 `user_info` 被两个测试用例使用。每个测试用例执行前，默认都会执行一次 `user_info`。

执行顺序大致为：

```text
执行 user_info
执行 test_user_name

执行 user_info
执行 test_user_role
```



#### Fixture 前置操作

如果测试用例执行前需要准备环境，可以写在 Fixture 中。

```python
import pytest


@pytest.fixture
def login():
    print("前置：执行登录操作")
    token = "token_abc123"
    return token


def test_query_order(login):
    print("执行：查询订单接口")
    assert login == "token_abc123"
```

执行顺序：

```text
前置：执行登录操作
执行：查询订单接口
```



#### Fixture 后置操作

Fixture 中使用 `yield`，`yield` 前面的代码是前置操作，`yield` 后面的代码是后置操作。

```python
import pytest


@pytest.fixture
def db():
    print("前置：连接数据库")
    db_conn = "mysql_connection"

    yield db_conn

    print("后置：关闭数据库连接")


def test_query_user(db):
    print("执行：查询用户数据")
    assert db == "mysql_connection"
```

执行顺序：

```text
前置：连接数据库
执行：查询用户数据
后置：关闭数据库连接
```

注意：

- `return` 只能返回数据，不能在返回后继续做后置清理
- `yield` 可以把数据传给测试用例，并在测试用例执行结束后继续执行后置代码
- 做数据库关闭、浏览器退出、测试数据删除时，通常用 `yield`



#### Fixture 互相调用

Fixture 可以直接依赖另一个 Fixture。

写法和测试用例使用 Fixture 一样：把另一个 Fixture 的名字写到当前 Fixture 的参数中。

```python
import pytest


@pytest.fixture
def base_url():
    return "https://api.example.com"


@pytest.fixture
def login_token(base_url):
    print(f"请求登录接口：{base_url}/api/login")
    return "token_abc123"


def test_get_user_info(login_token):
    assert login_token == "token_abc123"
```

执行逻辑：

```text
test_get_user_info 需要 login_token
login_token 又需要 base_url
所以 PyTest 先执行 base_url
再执行 login_token
最后执行 test_get_user_info
```

再看一个更接近接口自动化的例子：

```python
import pytest
import requests


@pytest.fixture
def base_url():
    return "https://api.example.com"


@pytest.fixture
def login_data():
    return {
        "username": "zhangsan",
        "password": "123456"
    }


@pytest.fixture
def token(base_url, login_data):
    response = requests.post(
        url=f"{base_url}/api/login",
        json=login_data
    )
    return response.json()["data"]["token"]


def test_get_cart_list(base_url, token):
    response = requests.get(
        url=f"{base_url}/api/cart/list",
        headers={"Authorization": f"Bearer {token}"}
    )

    assert response.status_code == 200
```

这里的关系是：

```text
token 依赖 base_url 和 login_data
test_get_cart_list 依赖 base_url 和 token
PyTest 会自动分析依赖关系，并按正确顺序执行
```

注意：不要让 Fixture 之间形成循环依赖。

错误示例：

```python
@pytest.fixture
def fixture_a(fixture_b):
    return "a"


@pytest.fixture
def fixture_b(fixture_a):
    return "b"
```

这种写法中 `fixture_a` 需要 `fixture_b`，`fixture_b` 又需要 `fixture_a`，PyTest 无法判断到底先执行谁。



#### 一个测试用例使用多个 Fixture

一个测试用例可以在参数中写多个 Fixture 名称。

```python
import pytest


@pytest.fixture
def username():
    return "zhangsan"


@pytest.fixture
def password():
    return "123456"


@pytest.fixture
def expected_code():
    return 0


def test_login(username, password, expected_code):
    result = login(username, password)
    assert result["code"] == expected_code


def login(username, password):
    if username == "zhangsan" and password == "123456":
        return {"code": 0, "message": "登录成功"}
    return {"code": 10001, "message": "登录失败"}
```

执行测试用例前，PyTest 会先准备 `username`、`password`、`expected_code`。



#### 一个 Fixture 给多个测试用例使用

一个 Fixture 可以被多个测试用例复用。

```python
import pytest


@pytest.fixture
def token():
    print("执行登录，获取 token")
    return "token_abc123"


def test_get_user_info(token):
    print("查询用户信息")
    assert token.startswith("token")


def test_get_order_list(token):
    print("查询订单列表")
    assert token == "token_abc123"


def test_get_cart_list(token):
    print("查询购物车列表")
    assert len(token) > 0
```

默认情况下，Fixture 的作用域是 `function`，也就是每个测试函数执行前都会执行一次。

所以上面的执行过程大致是：

```text
执行登录，获取 token
查询用户信息

执行登录，获取 token
查询订单列表

执行登录，获取 token
查询购物车列表
```

如果登录很耗时，并且多个用例可以共用同一个 token，可以通过 `scope` 控制只执行一次。



#### Fixture 的作用域 scope

Fixture 默认作用域是 `function`。

常见作用域：

| scope | 含义 | 常见场景 |
| --- | --- | --- |
| `function` | 每个测试函数执行一次，默认值 | 准备独立测试数据 |
| `class` | 每个测试类执行一次 | 一个测试类共用登录状态 |
| `module` | 每个测试文件执行一次 | 当前文件共用数据库连接、配置 |
| `package` | 每个测试包执行一次 | 一个测试包内共用资源 |
| `session` | 整个测试会话执行一次 | 全局配置、全局登录、启动服务 |

示例：`function` 级别

```python
import pytest


@pytest.fixture(scope="function")
def token():
    print("function 级别：每个测试用例执行前都会执行")
    return "token_abc123"


def test_case_01(token):
    assert token


def test_case_02(token):
    assert token
```

示例：`module` 级别

```python
import pytest


@pytest.fixture(scope="module")
def token():
    print("module 级别：当前文件只执行一次")
    return "token_abc123"


def test_case_01(token):
    assert token


def test_case_02(token):
    assert token
```

`scope="module"` 时，`token` 在当前测试文件中只执行一次，两个测试用例共用同一个返回值。

示例：`session` 级别

```python
import pytest


@pytest.fixture(scope="session")
def project_config():
    print("session 级别：整个测试运行过程中只执行一次")
    return {
        "base_url": "https://api.example.com",
        "env": "test"
    }
```

`session` 级别适合全局配置，但不要随便把所有 Fixture 都设置成 `session`。如果数据会被测试用例修改，共用同一份数据可能导致用例互相影响。



#### Fixture 自动执行 autouse

正常情况下，测试用例需要在参数中写 Fixture 名称，Fixture 才会执行。

如果设置 `autouse=True`，这个 Fixture 会在可见范围内自动执行。

```python
import pytest


@pytest.fixture(autouse=True)           # function级别
def print_log():
    print("每条用例执行前打印日志")


def test_case_01():
    assert True


def test_case_02():
    assert True
```

虽然 `test_case_01` 和 `test_case_02` 没有写 `print_log` 参数，但 `print_log` 仍然会自动执行。

适合使用 `autouse=True` 的场景：

- 每条用例执行前都要打印日志
- 每条用例执行前都要清理临时数据
- 每条用例执行后都要恢复环境
- 当前模块下所有用例都需要同一个前置动作

不建议滥用 `autouse=True`，因为它会让测试用例的依赖关系不够明显。一般只有“所有用例都必须执行”的公共动作才使用。



#### Fixture 参数化

Fixture 也可以参数化，让同一个 Fixture 返回多组数据。

```python
import pytest


@pytest.fixture(params=[
    {"username": "zhangsan", "password": "123456", "expected": 0},
    {"username": "zhangsan", "password": "error", "expected": 10001},
    {"username": "", "password": "123456", "expected": 10002},
])
def login_case(request):   # request是PyTest内置的Fixture，必须这么写
    return request.param


def test_login(login_case):
    result = login(login_case["username"], login_case["password"])
    assert result["code"] == login_case["expected"]


def login(username, password):
    if username == "":
        return {"code": 10002, "message": "用户名不能为空"}
    if password != "123456":
        return {"code": 10001, "message": "密码错误"}
    return {"code": 0, "message": "登录成功"}
```

这里 `login_case` 有三组参数，所以 `test_login` 会执行三次。

`request.param` 表示当前这一轮参数。

------

和 @pytest.mark.parametrize 结合

`@pytest.mark.parametrize` 更常用于测试用例参数化，Fixture 更常用于准备公共资源。

两者可以一起使用：

```python
import pytest


@pytest.fixture
def token():
    return "token_abc123"


@pytest.mark.parametrize(
    "product_id,expected_code",
    [
        (1001, 0),
        (1002, 0),
        (9999, 404),
    ]
)
def test_product_detail(token, product_id, expected_code):
    result = query_product(token, product_id)
    assert result["code"] == expected_code


def query_product(token, product_id):
    if token != "token_abc123":
        return {"code": 401, "message": "未登录"}
    if product_id == 9999:
        return {"code": 404, "message": "商品不存在"}
    return {"code": 0, "message": "查询成功"}
```

这个例子中：

- `token` 负责登录准备
- `parametrize` 负责提供多组商品 ID
- 测试用例同时使用 Fixture 和参数化数据

#### Fixture 重命名

有时 Fixture 函数名不想直接暴露给测试用例，可以使用 `name` 参数。

```python
import pytest


@pytest.fixture(name="token")
def get_login_token():
    return "token_abc123"


def test_user_info(token):
    assert token == "token_abc123"
```

测试用例使用的是 `token`，但真正的函数名是 `get_login_token`。



#### Fixture 测试控制

1、无条件跳过测试

使用 `@pytest.mark.skip`

这个测试永远不会执行。

```sql
import pytest

@pytest.mark.skip(reason="功能未开发完成")
def test_pay():
    assert 1 == 1
```



2、有条件跳过

```sql
import pytest
import sys

@pytest.mark.skipif(sys.version_info < (3, 10),
                    reason="需要 Python3.10 以上")
def test_new_feature():
    assert True
```







### ⭐conftest

`conftest.py` 是 PyTest 中专门用来放【公共 Fixture 和测试配置】的文件。

当多个测试文件都需要同一个 Fixture 时，不推荐每个文件都复制一份，而是把公共 Fixture 放到 `conftest.py` 中。

特点：

- 文件名必须叫 `conftest.py`
- 不需要手动导入，PyTest 会自动发现
- 通常放在测试目录下
- 当前目录和子目录中的测试文件可以直接使用其中的 Fixture
- 适合放登录、数据库连接、基础 URL、公共请求头、测试环境配置等



`conftest.py`：

```python
import pytest


@pytest.fixture(scope="session")
def base_url():
    return "https://api.example.com"


@pytest.fixture
def headers():
    return {
        "Content-Type": "application/json"
    }


@pytest.fixture
def token(base_url):
    print(f"请求登录接口：{base_url}/api/login")
    return "token_abc123"
```

`test_login.py`：

```python
def test_login(base_url, headers):
    assert base_url == "https://api.example.com"
    assert headers["Content-Type"] == "application/json"
```

`test_order.py`：

```python
def test_order_list(base_url, token):
    assert base_url.endswith("example.com")
    assert token == "token_abc123"
```

注意：`test_login.py` 和 `test_order.py` 中没有导入 `conftest.py`，但可以直接使用其中定义的 Fixture。

------

conftest 的作用范围

`conftest.py` 的作用范围和它所在目录有关。

示例：

```text
project/
├── conftest.py
├── test_login.py
└── api/
    ├── conftest.py
    ├── test_order.py
    └── test_cart.py
```

可以这样理解：

- `project/conftest.py` 中的 Fixture，`project` 目录及子目录下的测试文件都可以用
- `project/api/conftest.py` 中的 Fixture，主要给 `api` 目录及子目录下的测试文件使用
- 子目录中的 `conftest.py` 可以补充或覆盖上层目录的 Fixture

举例：

`project/conftest.py`：

```python
import pytest


@pytest.fixture
def base_url():
    return "https://api.example.com"
```

`project/api/conftest.py`：

```python
import pytest


@pytest.fixture
def token():
    return "token_for_api_tests"
```

`project/api/test_order.py`：

```python
def test_order(base_url, token):
    assert base_url == "https://api.example.com"
    assert token == "token_for_api_tests"
```

`test_order.py` 既能使用上层的 `base_url`，也能使用当前目录下的 `token`。

------

使用建议

1. 公共 Fixture 放到 `conftest.py`

   比如 `base_url`、`token`、`db`、`headers`。

2. 只给某个测试文件使用的 Fixture，可以直接写在当前测试文件中

   不要所有 Fixture 都塞进 `conftest.py`，否则后期会越来越乱。

3. Fixture 名称要清晰

   比如 `login_token` 比 `data` 更容易理解。

4. 不要在 Fixture 中写太多断言

   Fixture 主要负责准备数据和环境，真正的业务校验尽量放在测试用例里。

5. 注意 Fixture 作用域

   如果 Fixture 返回的数据会被测试用例修改，尽量使用默认的 `function` 级别，避免多个用例互相影响。



### ⭐Allure

Allure(/əˈlʊr/) 是一款自动化测试报告工具，它可以把 PyTest、JUnit、TestNG、Robot Framework 等测试框架的执行结果，转换成可视化程度很高的 HTML 测试报告。

简单理解：

- PyTest 负责执行测试用例
- `allure-pytest` 负责在执行过程中收集测试结果
- Allure 命令行工具负责把结果文件生成漂亮的测试报告

Allure 报告里通常可以看到：

- 用例总数、通过数、失败数、跳过数
- 每条用例的执行步骤
- 失败原因和断言信息
- 用例分组，比如模块、功能、故事
- 严重级别，比如 blocker、critical、normal、minor、trivial
- 附件，比如请求数据、响应数据、截图、日志、文本文件
- 执行环境，比如测试环境、Python 版本、接口地址
- 历史趋势、耗时统计、分类统计等

所以 Allure 比普通的 `pytest-html` 更适合项目汇报、自动化测试平台、持续集成流水线。

官方资料：

- Allure PyTest 文档：https://allurereport.org/docs/pytest/

4、创建 `mock_api.py` 和 `conftest.py`

“模拟接口请求”单独封装到 `mock_api.py` 文件中。

真实项目中，这个文件通常会继续封装 `requests.get()`、`requests.post()`、统一请求头、统一日志、统一异常处理等内容。

```python
import json
import time

import allure


class MockApiClient:
    """
    模拟接口客户端。

    当前案例没有真正请求服务器，所以用这个类模拟接口返回。
    真实项目中，可以把 requests.get() / requests.post() 封装到这个类中。
    """

    def __init__(self, base_url):
        # base_url 表示接口服务器地址，例如测试环境、预发布环境、正式环境。
        self.base_url = base_url


    def post(self, path, json_data=None, headers=None):
        """
        模拟发送 POST 请求。

        path：接口路径，例如 /api/login。
        json_data：请求体数据，一般是字典类型。
        headers：请求头，例如 token、Content-Type。
        """

        # 将测试过程拆分成多个可视化步骤，方便查看测试执行过程和定位问题
        with allure.step(f"发送 POST 请求：{path}"):
            # allure.attach() 可以把请求体、响应体、截图、日志等内容附加到 Allure 报告中。
            # json.dumps() 可以把 Python 字典转换成 JSON 字符串，方便报告展示。
            # ensure_ascii=False 表示中文不转义，indent=2 表示按 2 个空格缩进，美观易读。
            allure.attach(
                json.dumps(json_data, ensure_ascii=False, indent=2),
                name="请求体",
                attachment_type=allure.attachment_type.JSON
            )

            # time.sleep() 用来模拟接口耗时，让报告中能看到接口执行时间。
            time.sleep(0.1)

            if (
                path == "/api/login"
                and json_data["username"] == "zhangsan"
                and json_data["password"] == "123456"
            ):
                response = {
                    "code": 0,
                    "message": "登录成功",
                    "token": "mock-token-001",
                    "user": {"id": 1001, "name": "张三"}
                }
            elif path == "/api/login":
                response = {
                    "code": 1001,
                    "message": "账号或密码错误"
                }
            elif path == "/api/order/pay":
                response = {
                    "code": 3001,
                    "message": "支付渠道维护中"
                }
            else:
                response = {
                    "code": 404,
                    "message": "接口不存在"
                }

            # 把响应体也放到报告中。用例失败时，可以直接在报告里看到接口返回了什么。
            allure.attach(
                json.dumps(response, ensure_ascii=False, indent=2),
                name="响应体",
                attachment_type=allure.attachment_type.JSON
            )
            return response


    def get(self, path, headers=None):
        """
        模拟发送 GET 请求。

        GET 请求一般用于查询数据，请求参数通常放在 URL 或 params 中。
        这里为了简化案例，只根据 path 判断返回结果。
        """
        with allure.step(f"发送 GET 请求：{path}"):
            if path == "/api/goods/1001":
                response = {
                    "code": 0,
                    "message": "查询成功",
                    "data": {
                        "goods_id": 1001,
                        "goods_name": "iPhone18",
                        "price": 5499,
                        "stock": 100
                    }
                }
            else:
                response = {
                    "code": 404,
                    "message": "商品不存在"
                }

            allure.attach(
                json.dumps(response, ensure_ascii=False, indent=2),
                name="响应体",
                attachment_type=allure.attachment_type.JSON
            )
            return response
```

再创建 `conftest.py`：

`conftest.py` 中放公共 Fixture，比如接口地址、登录用户、接口客户端、登录 token、请求头、测试数据清理。

```python
import json

import allure
import pytest

from mock_api import MockApiClient


@pytest.fixture(scope="session")
def base_url():
    # scope="session" 表示整个测试会话只执行一次，适合放全局配置。
    return "https://api.shop.test"


@pytest.fixture(scope="session")
def test_user():
    # 测试账号统一放在 Fixture 中，后续用例直接引用，避免到处重复写。
    return {
        "username": "zhangsan",
        "password": "123456",
```

#### 使用建议

1. 用例标题要像手工测试用例标题一样清楚

   比如“正确账号和密码登录成功”，不要只写 `test_001`。

2. 用 `epic / feature / story` 按业务分层

   这样报告可以按业务模块查看，比只按文件名查看更适合汇报。

3. 关键请求和响应建议添加附件

   接口失败时，可以直接在报告中看到请求体、响应体、headers，不用重新翻控制台日志。

4. 失败用例要保留现场

   Web 自动化可以附加截图，接口自动化可以附加请求、响应、数据库查询结果。

5. 不要为了报告好看乱加步骤

   步骤应该围绕真实测试过程：准备数据、发送请求、检查结果、清理数据。

6. CI/CD 中生成静态报告

   Jenkins、GitLab CI、GitHub Actions 中通常使用 `allure generate` 生成静态报告，再把 `allure-report` 作为构建产物保存。

7. 每次执行前清理旧结果

   使用 `--clean-alluredir` 和 `allure generate --clean`，避免历史结果混入本次报告。

在接口自动化测试中，Requests 通常负责“发请求、拿响应”；PyTest 负责“组织用例、参数化、断言、Fixture 管理”；Allure 负责“生成测试报告、记录步骤、保留请求和响应现场”。

#### 发送 GET 请求

GET 请求通常用于查询数据，参数一般放在 URL 后面，也可以使用 `params` 传递。

```python
import requests

url = "https://api.example.com/api/goods"
params = {
    "keyword": "phone",
    "page": 1,
    "page_size": 10
}

headers = {
    "Accept": "application/json",
    "User-Agent": "api-autotest/1.0"
}

response = requests.get(
    url=url,
    params=params,
    headers=headers,
    timeout=10
)

print(response.status_code)
print(response.url)
print(response.json())
```

上面代码最终请求地址类似：

```text
https://api.example.com/api/goods?keyword=phone&page=1&page_size=10
```

常见断言：

```python
assert response.status_code == 200
assert response.json()["code"] == 0
assert len(response.json()["data"]["list"]) > 0
```

这段 GET 请求里有几个重点：

- `url`：接口地址，可以是完整地址，也可以在封装后使用 `base_url + path`
- `params`：查询参数，Requests 会自动拼接到 URL 后面，并处理 URL 编码
- `headers`：请求头，用来告诉服务端客户端希望接收 JSON、当前脚本身份、登录凭证等信息
- `timeout`：超时时间，单位是秒，建议每个接口都写，避免服务无响应时自动化脚本一直卡住
- `response`：响应对象，里面保存了状态码、响应头、响应体、最终请求 URL 等信息

GET 请求常用参数：

| 参数 | 作用 | 示例 |
| --- | --- | --- |
| `params` | URL 查询参数 | `params={"page": 1, "page_size": 10}` |
| `headers` | 请求头 | `headers={"Authorization": "Bearer token"}` |
| `cookies` | 手动携带 Cookie | `cookies={"session_id": "abc123"}` |
| `timeout` | 请求超时时间 | `timeout=10` |
| `verify` | 是否校验证书 | `verify=False` 可临时跳过 HTTPS 证书校验 |

接口测试中常见的 GET + Token 写法：

```python
import requests

token = "jwt_token_value"

response = requests.get(
    url="https://api.example.com/api/user/profile",
    params={"detail": "yes"},
    headers={
        "Accept": "application/json",
        "Authorization": f"Bearer {token}"
    },
    timeout=10
)

assert response.status_code == 200
assert response.json()["code"] == 0
assert response.json()["data"]["username"] == "test001"
```

在 PyTest 里可以直接把 GET 请求写成测试用例：

```python
import requests


def test_query_goods_success():
    response = requests.get(
        url="https://api.example.com/api/goods",
        params={"keyword": "phone", "page": 1, "page_size": 10},
        headers={"Accept": "application/json"},
        timeout=10
    )

    result = response.json()

    assert response.status_code == 200
    assert result["code"] == 0
    assert isinstance(result["data"]["list"], list)
```

响应对象常用属性和方法：

| 属性 / 方法 | 作用 | 常见用法 |
| --- | --- | --- |
| `response.status_code` | HTTP 状态码 | 判断是否为 `200`、`201`、`400`、`401` |
| `response.url` | 最终请求地址 | 检查 `params` 是否正确拼接 |
| `response.headers` | 响应头 | 查看 `Content-Type`、`Set-Cookie` |
| `response.cookies` | 响应 Cookie | 获取服务端写回的 Cookie |
| `response.text` | 字符串响应体 | 响应不是 JSON 时使用 |
| `response.json()` | 把 JSON 响应体转成字典 / 列表 | 接口自动化最常用 |
| `response.elapsed.total_seconds()` | 响应耗时 | 断言接口响应时间 |

例如断言响应时间：

```python
assert response.elapsed.total_seconds() < 2
```

如果接口返回的不是合法 JSON，`response.json()` 会报错。测试时可以先看响应头，或者在封装里统一处理。



#### 发送 POST 请求

POST 请求通常用于新增数据、登录、提交表单等。

1、发送 JSON 请求体

```python
import requests

url = "https://api.example.com/api/login"
body = {
    "username": "test001",
    "password": "123456"
}

headers = {
    "Content-Type": "application/json",
    "Accept": "application/json"
}

response = requests.post(url, json=body, headers=headers, timeout=10)

print(response.status_code)
print(response.json())
```

使用 `json=body` 时，Requests 会自动把字典转换成 JSON 字符串，并自动补充类似 `Content-Type: application/json` 的请求头。实际项目里仍然经常手动写 `Content-Type` 和 `Accept`，这样请求意图更清楚，也方便和接口文档对照。

2、发送表单请求体

```python
import requests

url = "https://api.example.com/api/login"
form_data = {
    "username": "test001",
    "password": "123456"
}

headers = {
    "Content-Type": "application/x-www-form-urlencoded"
}

response = requests.post(url, data=form_data, headers=headers, timeout=10)
print(response.json())
```

注意：

- `json=`：发送 JSON 格式请求体
- `data=`：发送表单格式请求体，或者发送原始字符串
- `files=`：上传文件时使用
- `params=`：POST 也可以带 URL 查询参数，比如 `/api/orders?coupon_id=888`
- `headers=`：POST 请求经常需要 `Content-Type`、`Authorization`、`X-Request-Id`
- `timeout=`：控制等待时间，接口自动化中建议统一设置
- 接口文档要求 JSON 就用 `json=`
- 接口文档要求 form 表单就用 `data=`

POST 请求里最容易混淆的是请求体格式和请求头。常见请求头如下：

| 请求头 | 作用 |
| --- | --- |
| `Content-Type` | 告诉服务端请求体是什么格式 |
| `Accept` | 告诉服务端客户端希望接收什么格式 |
| `Authorization` | 登录鉴权信息，比如 JWT Token |
| `User-Agent` | 客户端类型，比如浏览器、App、脚本 |
| `Cookie` | Cookie 鉴权或会话信息 |
| `Referer` | 请求来源页面 |
| `X-Request-Id` | 请求链路追踪 ID |

常见 `Content-Type`：

| 请求体格式 | `Content-Type` | Requests 写法 |
| --- | --- | --- |
| JSON | `application/json` | `json=body` |
| 普通表单 | `application/x-www-form-urlencoded` | `data=form_data` |
| 文件上传 | `multipart/form-data` | `files=files`，通常不用手动写 `Content-Type` |
| 原始文本 | `text/plain` | `data="hello"` |

示例：登录拿到 JWT Token，再携带 Token 创建订单。

```python
import requests

login_response = requests.post(
    url="https://api.example.com/api/login",
    json={"username": "test001", "password": "123456"},
    headers={"Accept": "application/json"},
    timeout=10
)

assert login_response.status_code == 200
login_result = login_response.json()
assert login_result["code"] == 0

token = login_result["data"]["jwt_token"]

create_order_response = requests.post(
    url="https://api.example.com/api/orders",
    params={"coupon_id": 888},
    json={"goods_id": 1001, "num": 1},
    headers={
        "Accept": "application/json",
        "Content-Type": "application/json",
        "Authorization": f"Bearer {token}",
        "X-Request-Id": "order_001"
    },
    timeout=10
)

result = create_order_response.json()
assert create_order_response.status_code == 200
assert result["code"] == 0
assert result["data"]["order_status"] == "created"
```

`Authorization: Bearer token` 是接口自动化中非常常见的鉴权方式。一般流程是：先调用登录接口，拿到 `access_token` 或 `jwt_token`，再把 token 放到后续接口请求头中。

#### Session 会话

如果多个接口需要共用 Cookie、连接池、公共请求头，可以使用 `requests.Session()`。

普通 `requests.get()`、`requests.post()` 每次看起来都是独立请求；`Session` 更像一个“持续打开的客户端”。登录接口返回的 Cookie、统一请求头、连接复用等信息，可以在同一个 Session 中继续使用。

```python
import requests

# 创建一个 Session 对象。
# 可以把它理解成一个会一直保持登录状态的“请求客户端”。
with requests.Session() as session:
    # 设置公共请求头。
    # 后面用这个 session 发送的请求，默认都会带上这些 Header。
    session.headers.update({
        "User-Agent": "api-autotest/1.0",
        "Accept": "application/json"
    })

    # 第一步：调用登录接口。
    # 如果服务端通过 Cookie 记录登录状态，登录成功后 Cookie 会自动保存到 session 里。
    login_response = session.post(
        url="https://api.example.com/api/login",
        json={"username": "test001", "password": "123456"},
        timeout=10
    )

    # 断言登录接口本身是成功的。
    assert login_response.status_code == 200
    assert login_response.json()["code"] == 0

    # 第二步：继续用同一个 session 请求个人信息接口。
    # 如果登录接口返回过 Cookie，这里会自动带上，不需要手动拼 Cookie。
    profile_response = session.get(
        url="https://api.example.com/api/user/profile",
        timeout=10
    )
```

`Session` 的好处：

- 自动保持 Cookie
- 复用 TCP 连接，提高执行效率
- 可以统一设置公共请求头
- 适合一个测试类或一次测试流程中连续调用多个接口
- 适合放到 PyTest Fixture 里，供多个用例复用

Cookie 登录系统中，`Session` 尤其常用。比如登录成功后，服务端通过响应头 `Set-Cookie` 返回 `session_id`，后续查询个人信息、购物车、订单时，Session 会自动把 Cookie 带上。

```python
import requests

# Cookie 登录系统常见流程：
# 1. 先登录
# 2. 服务端通过 Set-Cookie 返回 session_id
# 3. 后续请求自动携带这个 Cookie
with requests.Session() as session:
    # 这里使用 data=，表示按普通表单方式提交账号密码。
    login_response = session.post(
        url="https://api.example.com/api/login",
        data={"username": "test001", "password": "123456"},
        timeout=10
    )

    # 查看当前 session 中保存了哪些 Cookie。
    # 如果登录成功，通常能看到 session_id、JSESSIONID 等值。
    print(session.cookies)

    # 查询购物车接口。
    # 这次请求会自动带上登录时保存的 Cookie。
    cart_response = session.get(
        url="https://api.example.com/api/cart/items",
        timeout=10
    )

    # 只要 Cookie 还有效，服务端就能识别当前用户是谁。
    assert cart_response.status_code == 200
```

如果系统不是 Cookie 鉴权，而是 Token 鉴权，也可以登录后把 Token 更新到 Session 的公共请求头中。

```python
import requests

# Token 登录系统常见流程：
# 1. 调登录接口拿到 token
# 2. 把 token 放到 Authorization 请求头中
# 3. 后续请求自动携带 Authorization
with requests.Session() as session:
    # 先设置所有接口都通用的请求头。
    session.headers.update({
        "Accept": "application/json",
        "User-Agent": "api-autotest/1.0"
    })

    # 登录接口返回 jwt_token。
    login_response = session.post(
        url="https://api.example.com/api/login",
        json={"username": "test001", "password": "123456"},
        timeout=10
    )

    # 从登录响应 JSON 中取出 token。
    token = login_response.json()["data"]["jwt_token"]

    # 把 token 放到 Session 的公共 Header 中。
    # 后面用 session 发请求时，都会自动带上 Authorization。
    session.headers.update({
        "Authorization": f"Bearer {token}"
    })

    # 创建订单接口需要登录。
    # 因为前面已经设置了 Authorization，这里不用再单独传 headers。
    order_response = session.post(
        url="https://api.example.com/api/orders",
        json={"goods_id": 1001, "num": 1},
        timeout=10
    )

    # 断言订单创建成功。
    assert order_response.status_code == 200
    assert order_response.json()["code"] == 0
```

在 PyTest 中，常把 Session 封装成 Fixture：

```python
import pytest
import requests


# scope="session" 表示这个 Fixture 在一次 pytest 运行中只创建一次。
# 多个测试用例都可以复用同一个 api_session。
@pytest.fixture(scope="session")
def api_session():
    # 创建 Session，并在用例执行结束后自动关闭。
    with requests.Session() as session:
        # 设置公共 Header。
        session.headers.update({
            "Accept": "application/json",
            "User-Agent": "api-autotest/1.0"
        })

        # 在 Fixture 中先完成登录。
        # 这样测试用例里就不用重复写登录代码。
        login_response = session.post(
            url="https://api.example.com/api/login",
            json={"username": "test001", "password": "123456"},
            timeout=10
        )
        assert login_response.status_code == 200

        # 从登录响应中取 token。
        token = login_response.json()["data"]["jwt_token"]

        # 把 token 写入公共 Header。
        # 后面的所有接口请求都会默认带上登录凭证。
        session.headers.update({
            "Authorization": f"Bearer {token}"
        })

        # yield 前面的代码：测试用例执行前的准备工作。
        # yield 出去的 session 会传给需要 api_session 的测试用例。
        yield session

        # yield 后面如果继续写代码，就是测试结束后的清理工作。
        # 当前例子没有额外清理，所以这里不需要写内容。

# 测试函数参数名叫 api_session，pytest 会自动调用上面的 Fixture。
def test_query_order_success(api_session):
    # 使用已经登录过的 api_session 请求订单详情。
    response = api_session.get(
        url="https://api.example.com/api/orders/10001",
        timeout=10
    )

    # 把响应体转成 Python 字典，方便断言字段。
    result = response.json()

    # 断言 HTTP 状态码、业务 code、订单 ID。
    assert response.status_code == 200
    assert result["code"] == 0
    assert result["data"]["order_id"] == 10001
```

使用 Session 时要注意：

- 公共 Header 会影响后续所有请求，如果某个接口需要特殊 Header，可以在单次请求中传 `headers=`
- 单次请求传入的 `headers` 会和 Session 公共 Header 合并，但同名字段会覆盖公共 Header
- Cookie 会自动保存和发送，测试不同账号时不要混用同一个 Session
- Fixture 的 `scope="session"` 表示整个测试运行期间共用一个 Session，适合登录一次后执行很多接口
- 如果每条用例都需要独立登录状态，可以把 Fixture 改成 `scope="function"`

##### 3、封装请求客户端

`common/api_client.py`

```python
import json
import allure
import requests


class ApiClient:
    def __init__(self, base_url):
        self.base_url = base_url.rstrip("/")
        self.session = requests.Session()
        self.session.headers.update({
            "Accept": "application/json",
            "User-Agent": "api-autotest-demo/1.0"
        })

    def request(self, method, path, params=None, json_data=None, headers=None):
        url = f"{self.base_url}{path}"
        method = method.upper()

        with allure.step(f"发送 {method} 请求：{path}"):
            response = self.session.request(
                method=method,
                url=url,
                params=params,
                json=json_data,
                headers=headers,
                timeout=10
            )

        self.attach_request_response(method, url, params, json_data, headers, response)
        return response

    @staticmethod
    def attach_request_response(method, url, params, json_data, headers, response):
        request_info = {
            "method": method,
            "url": url,
            "params": params,
            "json": json_data,
            "headers": headers
        }
        allure.attach(
            json.dumps(request_info, ensure_ascii=False, indent=2),
            name="请求信息",
            attachment_type=allure.attachment_type.JSON
        )

        try:
            response_body = response.json()
        except ValueError:
            response_body = response.text

        allure.attach(
            json.dumps(response_body, ensure_ascii=False, indent=2) if isinstance(response_body, dict) else response_body,
            name="响应信息",
            attachment_type=allure.attachment_type.JSON
        )
```

##### 6、编写统一接口测试用例

`tests/test_api_cases.py`

```python
import allure
import pytest


def get_value_by_path(data, path):
    """根据 data.goods_id 这种点号路径从响应 JSON 中取值。"""
    current = data
    for key in path.split("."):
        current = current[key]
    return current


def replace_context_vars(value, context):
    """把 /api/orders/${order_id} 替换成真实订单 ID。"""
    if not isinstance(value, str):
        return value

    for key, real_value in context.items():
        value = value.replace("${" + key + "}", str(real_value))
    return value


@allure.epic("电商系统")
@allure.feature("接口自动化数据驱动")
@pytest.mark.api
def test_api_by_excel_or_mysql(case, api_client, auth_headers, context):
    allure.dynamic.title(case["title"])
    allure.dynamic.story(case["case_id"])

    method = case["method"]
    path = replace_context_vars(case["path"], context)
    params = case.get("params") or {}
    body = case.get("body") or {}
    headers = case.get("headers") or {}

    if str(case.get("need_token")).lower() == "yes":
        headers.update(auth_headers)

    response = api_client.request(
        method=method,
        path=path,
        params=params,
        json_data=body,
        headers=headers
    )

    response_json = response.json()

    with allure.step("断言 HTTP 状态码"):
        assert response.status_code == int(case["expected_status"])

    with allure.step("断言业务 code"):
        assert response_json["code"] == int(case["expected_code"])

    expected_key = case.get("expected_key")
    expected_value = case.get("expected_value")
    if expected_key:
        actual_value = get_value_by_path(response_json, expected_key)
        assert str(actual_value) == str(expected_value)

    if case["case_id"] == "order_001":
        context["order_id"] = response_json["data"]["order_id"]
```

##### 8、案例流程说明

这个案例执行时，大致流程如下：

1. PyTest 收集测试用例
2. `pytest_generate_tests` 根据 `--case-source` 读取 Excel 或 MySQL
3. `api_client` Fixture 创建统一请求对象
4. `jwt_token` Fixture 调用登录接口获取 JWT Token
5. 普通 GET 接口直接发送请求
6. 需要鉴权的 POST / GET 接口自动加 `Authorization` 请求头
7. 创建订单接口返回 `order_id` 后保存到 `context`
8. 查询订单详情接口使用 `${order_id}` 读取上一个接口返回的数据
9. Allure 保存每条用例的请求信息、响应信息、断言步骤

##### 9、实际项目优化方向

1. 配置独立管理

   `base_url`、数据库账号、测试账号密码不要写死在代码中，可以放到 `config.yaml`、环境变量或 CI/CD 变量里。

2. 密码和 Token 不要明文提交

   真实项目中不要把生产账号、密码、Token 写进 Git 仓库。

3. 请求封装要统一处理异常

   比如超时、连接失败、非 JSON 响应、HTTP 500 等，都要在报告里保留现场。

4. 数据依赖要可控

   接口之间可以有关联，但不要让大量用例互相依赖，否则一个接口失败会导致后面大片失败。

5. 测试数据要能清理

   创建订单、创建用户、创建商品后，最好有后置清理逻辑，避免测试环境数据越来越脏。

6. 断言不能只看状态码

   需要同时断言 HTTP 状态码、业务状态码、关键字段、数据库落库结果，必要时还要断言响应时间。
